# TASK 04 — программа управляемых испытаний (TASK 05, черновик к запуску)

Документ описывает, **что именно** будет запущено на реальных API при
отдельном разрешении владельца, сколько это может стоить и по каким критериям
приёмка считается успешной. В TASK 04 ни один платный запрос не выполнялся.

## 1. Условия запуска (явное действие пользователя)

Ничего не запускается само: обычный `flutter test` (и CI) не отправляет
платных запросов — live-файлы под тегом `live`, а весь набор `test/live`
дополнительно требует `CARDFLOW_LIVE_TESTS=1`.

Переменные окружения управляемого набора (`test/live/adaptive_generation_live_test.dart`):

| Переменная | Значение по умолчанию | Смысл |
|---|---|---|
| `CARDFLOW_LIVE_TESTS` | не задана (запросы запрещены) | явное разрешение live-прогона |
| `CARDFLOW_LIVE_PROVIDER` | `deepseek` | id пресета каталога |
| `CARDFLOW_LIVE_MODEL` | модель пресета | id модели |
| `CARDFLOW_LIVE_MAX_REQUESTS` | `0` | лимит логических запросов |
| `CARDFLOW_LIVE_MAX_COST_USD` | `0` | лимит предварительной стоимости |
| `CARDFLOW_LIVE_ALLOW_UNKNOWN_COST` | не задана | разрешить прогон при неизвестном тарифе (ручное решение) |
| `CARDFLOW_LIVE_TIMEOUT_SEC` | `120` | таймаут одного HTTP-запроса |
| `CARDFLOW_LIVE_ENABLE_PROMPT_ONLY` | не задана | Test A/B |
| `CARDFLOW_LIVE_ENABLE_MATERIALS` | не задана | Test C/D |
| `CARDFLOW_LIVE_ENABLE_IMAGES` | не задана | Test E |
| `CARDFLOW_LIVE_ENABLE_RECOVERY` | не задана | Test F (симуляция, без оплаты) |
| `CARDFLOW_LIVE_VISION` | по каталогу | считать модель видящей изображения |
| `CARDFLOW_LIVE_REPORT` | `build/live/live-runs.jsonl` | файл отчёта прогона |
| `DEEPSEEK_API_KEY` | — | ключ (значение не печатать) |

Команда (ключ — только из окружения, значение не выводить):

```
# PowerShell: ключ уже в User scope; в процесс агента он не наследуется —
# читать из реестра и передавать дочернему процессу (L30).
$env:CARDFLOW_LIVE_TESTS="1"
$env:CARDFLOW_LIVE_PROVIDER="deepseek"
$env:CARDFLOW_LIVE_MODEL="deepseek-flash"
$env:CARDFLOW_LIVE_MAX_REQUESTS="15"
$env:CARDFLOW_LIVE_MAX_COST_USD="0.12"
$env:CARDFLOW_LIVE_ENABLE_PROMPT_ONLY="1"
$env:CARDFLOW_LIVE_ENABLE_MATERIALS="1"
fvm flutter test test/live/adaptive_generation_live_test.dart --tags live --no-pub
```

Остановить прогон немедленно: `Ctrl+C` (бюджет и таймауты ограничивают расход
даже при сбое), затем `fvm flutter test` без `--tags live` — ничего не
отправится.

## 2. Сценарии

### Test A — короткий prompt-only (3 карточки)

- Материалы: нет; тема «Круговорот воды в природе…» (`liveWishesShort`).
- Проверяется: сборка запроса, системный промпт, JSON-схема, разбор карточек,
  локальная схема A8.4, `usage`, предпросмотр (карточки в результате).
- Ожидания: `status=done`, 1–3 карточки, `usage` присутствует, нет пустых
  полей и дублей, `estimatedInputTokens` близки к `actualInputTokens`
  (калибровка запишет отношение).

### Test B — 20 карточек prompt-only

- 3 запроса (7 карточек/запрос по лимиту вывода 8192).
- Проверяется: `GenerationContinuityState` (сводка уже созданных карточек в
  каждом следующем запросе), сумма лимитов = 20, отсутствие повторов,
  согласованность терминов (вручную), сохранение пожеланий.
- Ожидания: `chunkCount ≥ 2`, сумма `<limit>` = 20, ≥ 10 карточек, 0 дублей.

### Test C — небольшой текстовый документ (6 карточек)

- Материал: `liveSmallDocument()` (3 раздела: испарение, конденсация, осадки).
- Проверяется: извлечение текста (фикстура — уже разобранный `ParsedDocument`),
  `ContentInventory`, планирование, передача контента, соответствие карточек
  материалу (вручную), `source_excerpt` (если модель вернула), отсутствие
  потерь (`plan.omitted` пуст).
- Ожидания: `status=done`, `plan.isPromptOnly=false`, карточки не пусты,
  измеримые дефекты отсутствуют.

### Test D — большой текстовый документ (30 карточек)

- Материал: `liveBigDocument()` (8 разделов механики, ~9 тыс. символов).
- Проверяется: адаптивное дробление (несколько фрагментов), порядок
  (`chunks[i].index == i+1`), отсутствие пропущенных разделов (`omitted` пуст,
  покрытие единиц), частичный успех (ожидается `done`; при `partial` —
  разбор причин, а не «успех»).
- Ожидания: ≥ 2 фрагмента, `status=done`, `failures` пуст, ≥ 15 карточек.

### Test E — PDF с изображением (Vision)

- Материал: программный PDF со встроенным JPEG (`buildPdfWithEmbeddedImage`),
  разбирается production-`PdfParser` → `DocumentImage` → каталог `<images>` и
  image-части.
- Условие: `CARDFLOW_LIVE_VISION=1` (у пресета DeepSeek флага Vision нет, а
  официальная страница говорит, что `deepseek-flash` изображения принимает).
- Проверяется: image-части, реальные форматы (PNG/JPEG), размер запроса,
  фактическое участие изображений, статусы (`sentToModel`), каталог, предпросмотр.
- Ожидания: `sentDocumentImageIds` не пуст, в `plan.images` есть
  `sentToModel`, карточки не пусты.
- Риск: `deepseek-flash` может не принять image-часть (тогда `visionUnsupported`
  или 400) — это фиксируется как результат, а не маскируется.

### Test F — восстановление после ошибки (без оплаты)

Платных ошибок искусственно не создаём. Доступные механизмы симуляции:

1. **Локальный HTTP-endpoint** (`test/live/support/local_provider_server.dart`)
   — реализован и покрыт офлайновым тестом
   `test/integration/generation_recovery_http_test.dart` (10 тестов, реальный
   сокет loopback): 413, 429 + `Retry-After` (120 с и 0 с), таймаут приёма,
   400 с текстом переполнения контекста, битый JSON, обрезанный ответ
   (`finish_reason=length`), 5xx с повторами, 401, обрыв соединения.
2. **`FakeGenerationTransport` / `FakeHttpAdapter`** — существующие
   unit/integration-тесты пайплайна (дробление, сокращение вывода, бюджет
   восстановления, `Retry-After` в сбое фрагмента).
3. **Реальный провайдер** — только после отдельного разрешения; для этого
   сценария дорогой повтор не нужен: достаточно A/B-прогона, где видно
   `recoveryRequestsUsed`.

Итог: Test F **выполним офлайн** и не требует денег; живой recovery —
отдельное разрешение и отдельная смета (не входит в базовый план).

## 3. Предварительная стоимость (DeepSeek `deepseek-flash`)

Тариф: вход $0.30 / 1M, выход $1.20 / 1M (пиковый; off-peak вдвое дешевле) —
официальная страница DeepSeek, проверено 2026-11-19. Оценка — **верхняя**:
токены входа включают запас 10 % и полную обвязку; выход — ожидаемый текст,
а не резерв `max_tokens`.

| Сценарий | Запросы | Ожидаемые input tokens | Ожидаемые output tokens | Стоимость (оценка) |
|---|---:|---:|---:|---:|
| Test A — короткий prompt-only (3 карточки) | 1 | 7 800 | 1 500 | **$0.0041** |
| Test B — 20 карточек prompt-only | 3 | 27 000 | 10 500 | **$0.0207** |
| Test C — небольшой документ (6 карточек) | 1 | 8 200 | 3 000 | **$0.0061** |
| Test D — большой документ (30 карточек) | 5 | 50 000 | 17 500 | **$0.0360** |
| Test E — PDF с изображением (4 карточки, Vision) | 1 | 10 200 | 2 000 | **$0.0055** |
| **Итого A–E** | **11** | **103 200** | **34 500** | **≈ $0.0724** |
| **Минимальный безопасный набор A–C** | **5** | **43 000** | **15 000** | **≈ $0.0309** |

Оговорки (не выдавать за точное):

- строгий пробный запрос (`strict` → 400 у DeepSeek, ADR-021) в смете не
  учтён: отказ до генерации обычно не тарифицируется, но это **не
  подтверждено** официально — заложен риск +1 запрос на каждый сценарий
  (тогда A–E ≈ $0.084);
- возможные повторы 429/5xx увеличивают расход; бюджет запросов и лимит
  стоимости останавливают прогон;
- фактические токены придут в `usage` и будут записаны в отчёт калибровки —
  смета заменяется фактом после первого прогона;
- цены могут измениться: перед TASK 05 перепроверить официальную страницу.

Для остальных моделей стоимость **неизвестна** (тариф не подтверждён) →
`amount = null`, автоматический запуск блокируется до ручного разрешения
`CARDFLOW_LIVE_ALLOW_UNKNOWN_COST=1` после проверки тарифа.

## 4. Критерии качества карточек (независимая проверка)

Автоматически (измеримо, `LiveCardQualityReport`): дубликаты по `contentHashOf`,
пустые вопрос/ответ, длина вопроса > 500 и ответа > 2000 (жёстко), «мягкие»
пороги 200/1000, теги > 3, число пометок валидатора, наличие иллюстрации и
цитаты-источника. Успешный HTTP 200 **не** считается доказательством качества.

Вручную (чек-лист, 0/1/2 за пункт): корректность вопроса; корректность ответа;
соответствие исходному материалу; отсутствие выдуманных фактов; отсутствие
смысловых повторов; самодостаточность; отсутствие неоднозначности; сохранение
важных определений; разумная длина вопроса; разумная длина ответа. Для
prompt-only дополнительно: фактическая корректность, отсутствие противоречий
между карточками, согласованность терминологии, разумная полнота темы.

Формат отчёта — на сценарий: таблица авто-метрик (`toMarkdown`), затем
чек-лист с баллами и коротким комментарием, затем вердикт «принято / доработка»
с указанием, какие карточки (индексы) вызвали сомнение.

## 5. План TASK 05 — Controlled Live Generation Testing

**Предлагаемый объём (после разрешения владельца):**

| Шаг | Провайдер/модель | Сценарий | Запросов | Ожидаемые токены | Оценка |
|---|---|---|---:|---|---:|
| 5.1 | DeepSeek `deepseek-flash` | Test A | 1 | 7 800 in / 1 500 out | $0.0041 |
| 5.2 | DeepSeek `deepseek-flash` | Test B | 3 | 27 000 / 10 500 | $0.0207 |
| 5.3 | DeepSeek `deepseek-flash` | Test C | 1 | 8 200 / 3 000 | $0.0061 |
| 5.4 (условно) | DeepSeek `deepseek-flash` | Test D | 5 | 50 000 / 17 500 | $0.0360 |
| 5.5 (условно) | DeepSeek `deepseek-flash` | Test E (Vision) | 1 | 10 200 / 2 000 | $0.0055 |

Бюджет прогона: `CARDFLOW_LIVE_MAX_REQUESTS=15`, `CARDFLOW_LIVE_MAX_COST_USD=0.12`
(шаги 5.4/5.5 — только если 5.1–5.3 прошли).

**Риски:**

1. `deepseek-flash` отклонит strict-схему (как `deepseek-chat`) → лестница
   ADR-021 отработает; фиксируем `strict=400, tolerant=200`.
2. Идентификатор модели может быть недоступен аккаунту (402/404) → прогон
   останавливается, деньги не тратятся дальше; каталог помечается как
   устаревший (L137).
3. Модель вернёт меньше карточек, чем `<limit>` → это не ошибка; фиксируем
   достижимое число.
4. Vision у `deepseek-flash` может быть отклонён (400) → Test E помечается
   «не подтверждено», каталог/`supports_vision` не меняются без живого
   подтверждения.
5. Rate limit/сеть → `Retry-After` и бюджет; при исчерпании — partial, успешные
   карточки сохраняются.
6. Биллинг: строгий пробный 400 может тарифицироваться — заложен запас.

**Критерии успеха:**

- Test A: `done`, 1–3 карточки, `usage` есть, измеримых дефектов нет.
- Test B: ≥ 3 запроса, сумма лимитов = 20, ≥ 10 карточек, 0 дублей,
  продолжение не повторяет уже созданные карточки (ручная проверка).
- Test C: `plan.omitted` пуст, карточки соответствуют материалу (ручной балл
  ≥ 1 по каждому пункту чек-листа), измеримых дефектов нет.
- Test D: ≥ 2 фрагмента, `done`, порядок фрагментов 1..N, покрытие разделов.
- Test E: `sentDocumentImageIds` не пуст, статус `sentToModel`, карточки не пусты.
- Отчёт `build/live/live-runs.jsonl` заполнен; стоимость по факту не превышает
  лимит; ни одного лога с ключом/материалами.

**Остановка:** после отчёта TASK 04 работа останавливается; TASK 05 — только
по отдельному разрешению владельца.
