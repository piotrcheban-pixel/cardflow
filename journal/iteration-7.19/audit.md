# Аудит 7.19 — изображения карточек: первопричины и карта цепочки

**Дата:** 2026-11-21. **Снимок кода:** `16766f8` (ветка `main`,
`git status --porcelain` → пусто). **Итерация:** 7.19.

Аудит выполнен **до правок кода**. Источники фактов:

1. фактический код `lib/` (ссылки на строки — по снимку `16766f8`);
2. **фактическая БД владельца** — копия
   `%APPDATA%\ru.example\cardflow\cardflow\cardflow.sqlite`
   (`journal/iteration-7.19/owner-db-copy.sqlite`) и каталог медиа
   `%APPDATA%\ru.example\cardflow\cardflow\media\` (только чтение; копия сделана
   при закрытом приложении);
3. пользовательские скриншоты из задания (описание: «абстрактная синяя
   иллюстрация с геометрическими фигурами и графиком»);
4. `journal/STATE.md`, `journal/KNOWN_LIMITATIONS.md`, `AGENTS.md`, ADR-027,
   ADR-028, ADR-031 (итерация 7.14), ADR-037.

Бинарные данные изображений в отчёт и логи **не** записываются: только
SHA-256 (первые 16 hex), размер, MIME, провайдер и id.

## 1. Ответ на главный вопрос: откуда одинаковая картинка

**Одинаковая картинка — не исходное изображение и не общий fallback-asset.
Это локально нарисованная «заглушка» `PlaceholderImageGenerator`, которая
сохраняется в БД как обычное медиа карточки.**

Механизм (`lib/api/images/placeholder_image_generator.dart`,
`lib/api/generation/generation_pipeline.dart:1584`):

1. `GenerationPipeline._withCardImage` пытается привязать изображение к
   карточке: сначала по `image_id` из каталога `<images>`, затем внешним
   поиском по `image.query` / `image.fallback_query`.
2. Если **ни один** путь не дал результата (не нашлось файла по `image_id`,
   пустой запрос, исчерпан бюджет поиска, поиск вернул `null`, URL уже занят
   другой карточкой) — вызывается `_placeholderOrNothing`.
3. `_placeholderOrNothing` (если `placeholderGenerator != null`) рисует PNG
   800×450 (фото/иллюстрация) или 800×600 (схема): диагональный градиент,
   2–3 круга, две диагональные полосы и иконку вида
   (`photo` — солнце и горы, `diagram` — **оси и три столбика**, т.е. «график»,
   `illustration` — наложенные круг/квадрат/треугольник).
4. Seed заглушки — `contentHashOf(front, back)`; **палитра** —
   `hash % 8` из фиксированного набора из 8 пар цветов, **kind** — из ответа
   модели. Поэтому разные карточки получают **разные байты** (уникальный
   SHA-256), но **визуально почти одинаковую композицию**: например 68 из 80
   заглушек имеют `kind=diagram`, т.е. один и тот же график-столбики.
5. Заглушка — обычный `GeneratedCardImage` c `isPlaceholder: true` и
   `provider: 'placeholder'`; `DriftGenerationCardStore._writeImage`
   **сохраняет её в `MediaStore`, в строку `media` и в `media_json`** карточки,
   а `<файл>.meta.json` получает `isPlaceholder: true` и запрос модели.
6. `main.dart` после первого кадра запускает
   `CardImageRefresher.retryPlaceholders()`: при следующем старте с сетью
   пробует заменить до 5 заглушек; **если не получилось — заглушка остаётся**.

Именно поэтому дефект выглядит как «на разных карточках одна и та же
картинка, не связанная с содержимым»: это не подстановка одного asset-а по
ошибке сопоставления ID, а **массовая генерация декоративных PNG на месте
ненайденных изображений**.

## 2. Карта цепочки «документ → UI» (с точками отказа)

| # | Этап | Код | Что происходит | Точка отказа |
|---|---|---|---|---|
| 1 | Исходный документ | парсеры `lib/api/parsers/` | DOCX `word/media`+`r:embed`, PPTX `ppt/media`, ODT `Pictures/`, PDF XObject/страницы/области | мусор отбрасывается (L134): < 4 КБ, < 64 px, не JPEG/PNG, повторы SHA-256 |
| 2 | Извлечение | `DocumentImage` (`lib/domain/generation/document_image.dart`) | подпись, контекст, страница, байты, MIME, размеры | нет файла → нечего привязывать |
| 3 | Создание image ID | `withCatalogIds` (`generation_images.dart:26`) | `img1…imgN` по порядку каталога фрагмента | ID **позиционные**, а не контентные |
| 4 | Хранение байтов | в памяти (`DocumentImage.bytes`) до импорта | в БД попадают только выбранные моделью | — |
| 5 | Каталог | `buildImageCatalog` → `<images>` | `id \| файл \| подпись \| контекст` (+ `стр. N`) | — |
| 6 | Передача модели | `selectVisionDocumentImages` + `attachment_parts.dart` | ≤ 8 частей/24 МБ, остальные — только каталог | изображение вне `<focus>`/фрагмента модель не видит |
| 7 | Выбор модели | `gen-ru-v8`, Правило 7 | **обязательный** объект `image` у **каждой** карточки + `image_id` | принудительная картинка у всех карточек |
| 8 | Разбор ответа | `CardResponseSchema.splitValid` + `CardContentValidator._imageSelectionOf` | `image_id` вне каталога → обнуляется, пометка `imageIdUnknown` | карточка остаётся без id |
| 9 | Сопоставление | `GenerationPipeline._documentImageById` | точное совпадение строки id | привязка теряется |
| 10 | **Привязка** | `GenerationPipeline._withCardImage` | файл → поиск → **заглушка** | **рисование декоративного PNG** |
| 11 | Сохранение карточки | `DriftGenerationCardStore` | `media` + файл + `<path>.meta.json` + `media_json` (плоский массив) | заглушка неотличима от настоящего изображения |
| 12 | Получение из хранилища | `DriftCardMediaRepository.readMedia` | `media` → `MediaStore.readMedia`; нет файла → id просто отсутствует | молчаливый пропуск |
| 13 | Декодирование | `CardImageView` | `Image.memory`, `errorBuilder → _ImageSkeleton` | **ошибка маскируется скелетоном** |
| 14 | Отображение в UI | `CardContentView:49` | `card.mediaIds.first` **независимо от `side`** | **ответная картинка видна на лицевой стороне** |

## 3. Проверка по вопросам §0.1 (по каждому звену)

1. **Есть ли картинка в исходном документе?** В кейсе B — да, PNG 888×625
   116 027 Б из PDF (`provider=file`). В кейсе A исходного изображения нет:
   модель запросила внешний поиск (`image.query`).
2. **Появляется ли она среди извлечённых?** Кейс B — да, id каталога
   разрешён в байты до внешнего поиска. Кейс A — нет ни одного изображения в
   документе по этому разделу.
3. **С каким image ID регистрируется?** Кейс B — id каталога (`imgN`);
   кейс A — id нет, вместо него заглушка с новым UUID при импорте.
4. **Какое содержимое связано с ID?** Кейс B — байты PNG из PDF
   (116 027 Б, корректный PNG). Кейс A — нарисованный PNG 20–40 КБ.
5. **Передаётся ли содержимое модели?** Кейс B — да, каталог + Vision-часть.
   Кейс A — нет исходного изображения, только каталог (пустой).
6. **Какой ID возвращает модель?** Кейс B — валидный `image_id`; кейс A —
   `image_id: null` + `image.query`.
7. **Сохраняется ли соответствие ID и файла?** Да, но только для настоящих
   изображений; соответствие «ID ↔ реальное содержимое» нарушается
   **заглушкой**: новый UUID, которого не было в каталоге.
8. **Какую ссылку получает карточка?** `media_json: ["<uuid>"]` — плоский
   массив без указания стороны.
9. **Что фактически загружает renderer?** `mediaIds.first` — и для лицевой, и
   для обратной стороны.
10. **Заменяется ли ошибка общей картинкой?** Да, дважды: (а) на этапе
    привязки — заглушкой; (б) в UI — скелетоном `_ImageSkeleton` при ошибке
    декодирования (`card_image_view.dart:107-112`), т.е. ошибка неотличима от
    пустого слота.

Проверенные частные случаи:

| Случай | Факт |
|---|---|
| Исходный файл не существует | `_documentImageById` → `null`, затем поиск/заглушка |
| Пустые байты | парсер отбрасывает < 4 КБ; на импорте пустые байты **не проверяются** (D8) |
| Неверный MIME | не проверяется при импорте и чтении (D8) |
| Повреждённое изображение | сохраняется как файл, ошибка декодирования → скелетон (D7) |
| Storage lookup вернул `null` | id просто отсутствует в `Map`, UI рисует **ничего** без сообщения (D6) |
| ID существует, но чужого запуска | pipeline разрешает только каталог текущего фрагмента; в БД id глобально уникален (UUID) |
| Ошибка декодирования | маскируется скелетоном (D7) |
| Повторная генерация с устаревшей ссылкой | при повторной генерации создаётся новая карточка/медиа; старых ссылок нет |

## 4. Проверка §0.2: A или B

**Ответ: B — разные исходные изображения потерялись, а интерфейс показывает
универсальную (одну и ту же по композиции) картинку.** Уточнение: картинка не
«один asset по общему id», а **генерируется заново для каждой карточки**, но
из фиксированного набора из 8 палитр и 3 видов, поэтому визуально
неотличима. Ситуация A (модель назначила один и тот же исходный `image_id`
разным карточкам) в данных **не обнаружена**: у 80 заглушек 80 разных
SHA-256, у всех `provider=placeholder`, все id уникальны (UUID).

Диагностическая таблица (фрагмент; полные данные — `media_integrity.md`,
формируется `tool/media_integrity_report.dart` после фазы 1):

| Этап | Image ID | Source | Размер | MIME | Результат |
|---|---|---|---|---|---|
| Привязка | — (нет image_id) | `image.query=finite difference method grid diagram` | 800×600, 30 361 Б | image/png | **placeholder** — исходника нет |
| Привязка | — | `image.query=finite difference grid spacing diagram` | 800×600, 21 952 Б | image/png | **placeholder** |
| Привязка | — | `image.query=finite difference algebraic equation diagram` | 800×600, 31 114 Б | image/png | **placeholder** |
| Привязка | `imgN` (PDF) | `file`, PNG из PDF | 888×625, 116 027 Б | image/png | настоящий файл, но **сторона не сохранена** |
| Поиск | — | `wikimedia` `q=finite difference grid heat conduction diagram` | JPEG | image/jpeg | настоящий файл (внешний поиск сработал) |

Ключевой вывод: измерять надо не только совпадение id, но и **происхождение
байтов**. Универсальной «заглушки-ассета» в коде нет — есть генератор.

## 5. Первопричина №2: изображения не разделены по сторонам

1. Домен хранит **один плоский список**: `Card.mediaIds`
   (`lib/domain/cards/card.dart:113`), `CardDraft.mediaIds`,
   `GeneratedCard.imageId`/`image`.
2. БД: `media_json` — JSON-массив id без стороны; `media`-таблица не имеет
   колонки стороны. Схема БД в 7.19 **не менялась** (см. ADR-042).
3. Рендер: `CardContentView.build` (строка 49) берёт `card.mediaIds.first`
   **до** выбора стороны; параметр `side` влияет только на текст. Следствие:
   одна и та же картинка видна и до, и после переворота.
4. Схема ответа v8: одно поле `image_id` — модель **не может** выразить
   «это изображение — ответ». Правило 7 промпта требует картинку **у каждой**
   карточки.
5. Редактор (`card_form_screen.dart`) работает с одним изображением:
   `_imageBytes`, `_imageUpload`, `mediaIds.first`; второй стороны нет.
6. Предпросмотр (`generation_preview_screen.dart`) показывает одно
   изображение карточки без разделения сторон.

**Фактическое подтверждение на карточке владельца** (кейс B): карточка
`b3699b98…`, вопрос «Какой формулой рассчитывают фактическую
воздухопроницаемость окна?», ответ `G_ф = A_ок·ΔP^0.67 / R_и`; медиа —
`media/bad1959e-….png` (888×625, PNG, `provider=file`,
`isPlaceholder=false`) — это **изображение из PDF с той же формулой и её
расшифровкой**. По `CardContentView` оно показывается на лицевой стороне до
переворота: ответ раскрыт картинкой. Снимок —
локальный снимок медиа карточки (888×625, PNG; в git не коммитится).

## 6. Найденные дефекты (вход в план 7.19)

| ID | Уровень | Дефект |
|---|---|---|
| D1 | high | Заглушка генерируется и **сохраняется как медиа карточки** при любой неудаче привязки (`_placeholderOrNothing`, `GenerationPipeline:1584`) |
| D2 | high | Промпт v8 **требует** картинку каждой карточке → массовый внешний поиск → массовые заглушки (80/207) |
| D3 | high | Одна плоская коллекция `mediaIds`; `CardContentView` игнорирует сторону → ответная иллюстрация видна до переворота |
| D4 | high | Схема v8 не позволяет модели выбрать сторону; `image_id` один на карточку |
| D5 | high | `main.dart` запускает `retryPlaceholders()` — заглушки живут и обновляются при каждом старте |
| D6 | medium | Ошибка чтения медиа (нет строки/файла) не показывается: изображение просто исчезает |
| D7 | medium | Ошибка декодирования маскируется `_ImageSkeleton` — неотличима от загрузки |
| D8 | medium | При импорте/чтении не проверяются пустые байты, MIME по сигнатуре, целостность связей source→catalog→asset→card |
| D9 | medium | Дублирование одного id на обеих сторонах не диагностируется |
| D10 | low | Нет диагностического отчёта по происхождению изображений (невозможно отличить «не нашли» от «нашли не то») |

## 7. Противоречия задания с фактическим кодом

1. **`gen-ru-v8` уже используется** (production `systemPromptVersion`,
   `AGENTS.md`), поэтому новая версия — **`gen-ru-v9`**; v8 сохраняется
   дословно (`lib/api/prompts/system_prompt.dart`, `docs/prompts/gen-ru-v8.txt`).
2. В промпте v8 карточка содержит **девять** ключей (не восемь): `front`,
   `back`, `card_type`, `tags`, `hint`, `source_excerpt`, `source_file`,
   `image_id`, `image`. v9 заменяет `image_id` на два массива и делает
   `image` необязательным объектом со стороной.
3. Strict-схема A8.4 требует `image` у каждой карточки. В v9 `image`
   становится nullable-объектом; локальная терпимая схема принимает ответы
   v5/v6/v7/v8 (`image_id`, `image_query`, `image`) и v9.
4. Имя `image_id` в коде уже означало «id из `<images>`»; в задании
   `question_image_ids`/`answer_image_ids` — массивы. Совместимость: старый
   `image_id` → `question_image_ids` (лицевая сторона), `image` → внешний
   поиск для вопроса, если сторона не указана.
5. **Миграция БД не нужна**: сторона хранится в существующем `media_json`
   (JSON v2), `schemaVersion` не меняется. Это прямо расширяет «существующую
   модель через JSON» (фаза 5 задания).
6. Два файла `system_prompt.dart`: `lib/api/prompts/system_prompt.dart`
   (текст, 53 КБ) и `lib/api/generation/system_prompt.dart` (реэкспорт,
   500 Б) — правки только в первом.
7. `PlaceholderImageGenerator` нельзя просто «запретить промптом»: он
   вызывается при любом сбое поиска, независимо от текста промпта; промпт
   лишь увеличивает частоту (D2).
8. Требование «несколько изображений на каждой стороне» несовместимо с
   текущим `CardImageView` в цикле: нужно отрисовать список; высотные
   ограничения — по 220 px на изображение.

## 8. Что требуется доказать тестами (моделирование потери изображений)

Так как дефект **воспроизводится на текущем коде** (не «историческая»
проблема), красная фаза строится на сценариях, которые зафиксированы в §0.1:

- `image_id` найден в каталоге, но файла нет → карточка **без** изображения,
  пометка `imageIdUnknown`/`imageNotFound`, **никакого** нового asset;
- поиск вернул `null`/ошибку/пустой ответ → карточка без изображения;
- два разных исходника никогда не дают один и тот же asset;
- заглушка не создаётся ни при каком сбое (в сохранённых карточках нет
  `provider=placeholder`);
- пустые/повреждённые байты отклоняются до записи; MIME по сигнатуре;
- ошибка storage lookup/decode показывается явным состоянием, а не
  подменяется;
- после перезапуска настоящие изображения сохраняются;
- wholeDocument и fragmented используют изображения своего фрагмента;
- изображения одного запуска не попадают в другой.

## 9. Итог фазы 0

**Первопричина №1 (повторяющаяся картинка):** `GenerationPipeline
._placeholderOrNothing` + `PlaceholderImageGenerator` — при любой неудаче
привязки изображения рисуется декоративный PNG (градиент, круги, полосы,
иконка `diagram` = оси и столбики) из 8 фиксированных палитр, сохраняется как
обычное медиа карточки (`media`, файл, `<path>.meta.json`,
`isPlaceholder: true`) и по `main.dart` ещё и ретраится при старте. Промпт v8
