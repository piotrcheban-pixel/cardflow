## 1. Первопричина

Заказ обрезался **не** бюджетом модели, а мягкой ёмкостью материала:

- `CardAllocator.allocate` считал `target = min(requestedCards, Σ capacity)` и
  возвращал `belowRequested = true` (`card_allocator.dart`, было строки 350–360);
  `capacity = ceil(meaningfulWords / 40 × density)` — эвристика ADR-040 §5,
  названная в коде «мягкой», но работавшая как жёсткий потолок суммы;
- `PlanWarningCode.requestedAbovePlan` ставился по `belowRequested`, а ARB
  `generationPlanRequestedAboveAchievable` объясняла это «бюджетом модели» и
  советовала сменить модель;
- изменить `maxOutputTokens` (2 000 / 8 192 / 64 000) на число «может выдать»
  не влияло вообще — проверено зондом на `GenerationPlanBuilder`.

Число 32 — сумма мягких ёмкостей разделов конкретного материала; «16 на ответ»
из задания — `cardsFor(8192 − 2048 резерв рассуждения) = 16`.

Аудит: `journal/iteration-7.20/audit.md` (карта цепочки, ответы на все 10
проверок задания, 9 находок F1–F9).

## 2. Что сделано (ADR-043)

1. **Card Allocator** — мягкая ёмкость стала предпочтением: water-filling до
   ёмкости, затем остаток заказа распределяется по весам с точной целочисленной
   раздачей (`BigInt` для произведения «остаток × вес»). Итог: `Σ planned ==
   requestedCards`, если есть содержательные разделы. `belowRequested` остался
   только для «разделов нет вовсе».
2. **Отдельный статус материала** — `CardAllocation.estimatedCapacity` /
   `materialLimited` → `GenerationPlan.materialCapacity` / `materialLimited` →
   новый `PlanWarningCode.materialCapacityBelowRequested` («Материала хватает
   примерно на M карточек из N. Заказ сохранён полностью…»).
   `requestedAbovePlan` больше не упоминает бюджет модели.
3. **Output Batch Planner** — `batchCount = ⌈total / perBatch⌉` целочисленно
   (без переполнения), `batchSizes` заполняет партии до вместимости и отдаёт
   остаток последней; `batchSizesFor` используется, когда число партий задаёт
   раскладка изображений (сумма сохраняется при любом аргументе).
4. **Технический предохранитель** — `⌈заказ / cardsPerBatch⌉ + (части − 1) ≤
   maxChunks` проверяется **до** построения партий: `int.max` даёт явный
   `tooManyChunks`, а не ~10¹⁷ элементов списка.
5. **Оценка вывода** — резерв считается по максимальной партии, а не по сумме
   лимитов (при 500 карточках оценка больше не завышается в разы).
6. **Pipeline** — дополнительная партия перераспределения недостачи не больше
   вместимости одного ответа (`cardsPerBatch`, раньше константа 40).
7. **UI** — «Запрошено: N карточек» под полем (значение не меняется), «План:
   частей входа — X, партий — Y; запрошено — N, в плане — M», «Подробнее»:
   «Запрошено карточек», «Всего карточек в плане», «Максимум в одной партии»,
   «Распределение по партиям», «Ёмкость материала (оценка)»; предпросмотр
   результата: «Материал исчерпан: создано X карточек из N. Оставшиеся партии
   остановлены — карточки не выдумывались».

## 3. Конкретный пример (критерий §7 задания)

**Заказ 40, модель позволяет 16 карточек за один ответ** (`batchCardsCeiling`
16, `cardsFor(maxTokens) = 16`):

```
requestedCards = 40
cardsPerBatch  = 16
batchCount     = ⌈40 / 16⌉ = 3
sizes          = [16, 16, 8];  Σ = 40
материал       = достаточен (materialLimited = false)
тело запроса 4xx/ответов модели: нет
```

Тест фиксирует именно это: `card_order_plan_7_20_test.dart` →
`заказ 40 при вместимости 16 → 3 последовательные партии (16,16,8)`;
production-путь — `card_order_batches_flow_7_20_test.dart` →
`заказ 40: три последовательные партии, все 40 карточек сохранены`
(3 вызова модели с лимитами 16/16/8, 40 карточек в результате).

**Заказ 100 при вместимости 12** → `⌈100 / 12⌉ = 9` партий
`[12, 12, 12, 12, 12, 12, 12, 12, 4]`, сумма 100.
**Заказ 200 при вместимости 20** → 10 партий по 20.
**Заказ 40 при ёмкости материала 26** → в плане ровно 40 (2 партии 22 + 18,
дефолтный `cardsFor(8192) = 22`) и **отдельный** статус «Материала хватает
примерно на 26 карточек из 40»; сообщения про «бюджет модели» нет.
