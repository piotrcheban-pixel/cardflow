### H1. Импорт колоды не перепривязывает `fsrs_json` к новым id карточек → сессия импортированной колоды не запускается

| | |
|---|---|
| **Файл:строка** | `lib/data/transfer/drift_deck_transfer_service.dart:244` (копирование `fsrsJson` как есть) при `:190-192,224,231` (новые uuid карточек); `lib/domain/cards/card_scheduling.dart:38-44` (жёсткая проверка `scheduling.cardId == card.id`); `lib/data/transfer/zip_deck_archive_codec.dart:362,746` (экспорт/импорт `fsrs` — «сырая» строка); `lib/ui/review/review_session_screen.dart:51-79,351-371` (любая ошибка `start()` → постоянный error-экран); `docs/archive-format.md:122-134,146` |
| **Суть** | Импорт генерирует новые id колоды/карточек/медиа (это контракт формата), но `cards.fsrs_json` копирует байт-в-байт. В итерации 2 `CardSchedulingMapper.toSchedulingCard` требует, чтобы `fsrs_json.cardId` совпадал с `cards.id`, иначе бросает `FormatException` («fsrs_json принадлежит другой карточке»). Значит: колода, экспортированная **после повторений** (в `fsrs_json` — старый id), после импорта не может начать сессию, как только в очередь попадает хотя бы одна такая карточка — просроченная сразу, карточка с будущим `due` — в день повторения: `ReviewSessionEngine.start()` маппит все карточки очереди (`review_session_engine.dart:141-147`) и падает на первой же; `_load()` ловит исключение → `_loadFailed` → ARB «Не удалось загрузить карточки сессии.» + «Повторить» (ретрай обречён, пока карточка в очереди). Тот же эффект — для любого архива, где `fsrs` не является JSON-снимком `SchedulingCard` (например, фикстура `{"stability":12.5}` из тестов импорта итерации 1: теперь это невалидный формат), и если такая карточка в очереди. Дефект проявляется на основном сценарии «повторил → экспортировал → импортировал» и ломает **всю** сессию колоды (не одну карточку) |
| **Почему проблема** | SPEC A5 (`fsrs_json` — состояние FSRS карточки, участвует в планировании), A6.3/A7.2 (сессия из экрана колоды должна работать), A6.9 + docs/archive-format.md (экспорт/импорт `.zip` без потерь; id при импорте новые — контракт итерации 1). Это нарушение принципа «функция либо работает, либо её нет» для импортированных колод и регресс, не поймавший C6/T16 (в тестах нет сценария «импорт → сессия»). T3 объявлял `CardSchedulingMapper` единственным местом сведения `fsrs_json` и колонок — стык с импортом не учтён |
| **Как проверил** | 1) `fvm flutter test test/unit/data/transfer/deck_transfer_service_test.dart` → `+23: All tests passed!`; тест `:551 export → import → export без потери контента` проверяет `actual.id != expected.id` (`:593-594`) и через `_expectSameCardContent` (`:136`) `expect(actual.fsrsJson, expected.fsrsJson)` — т.е. **зелёный** тест фиксирует: id новый, `fsrs_json` старый (с прежним `cardId`). 2) `fvm flutter test test/unit/domain/card_scheduling_test.dart` → `+7: All tests passed!`; тест `fsrs_json чужой карточки — FormatException` (`:96-108`) фиксирует, что такой снимок — исключение. 3) Трассировка: `drift_deck_transfer_service.dart:190-192` (`newCardIds`), `:224,231` (новый id в строке), `:244` (`fsrsJson: Value(card.fsrsJson)`) → `card_scheduling.dart:38-44` → `review_session_screen.dart:72-77` → `:351-371`. E2E-тест «экспорт после повторения → импорт → сессия» в репозитории отсутствует (grep по тестам: нет ни одного вызова очереди/движка на импортированной колоде) |
| **Ожидаемое поведение** | Импортированная колода (в т.ч. выгруженная из этого же приложения после повторений) запускает классическую сессию; `fsrs_json` после импорта ссылается на **новый** id карточки (или `cardId` не является источником истины); невалидный/чужой `fsrs` не валит сессию: либо отклоняется импортом (`invalidCards`), либо документированно трактуется как «новая карточка» |
| **Требование к фиксу** | В `_prepareImport`: для `card.fsrsJson != null` — `jsonDecode` → `SchedulingCard.fromJson` (ошибка → `ArchiveException(invalidCards)` с путём) → заменить `cardId` на `newCardId` (и сверить `state`/`due` с колонками: сейчас `state=learning` при `fsrs=null` молча превращается в «новую» карточку — тоже зафиксировать) → re-encode в строку; обновить `docs/archive-format.md` (addendum: при импорте `fsrs` валидируется и перепривязывается к новому id; старый `cardId` не сохраняется); тесты: unit — «import перепривязывает fsrs к новому id», «невалидный fsrs → invalidCards»; интеграционный на production-провайдерах — оценка карточки → `exportDeckZip` → `importZip` → `ReviewSessionEngine.start()` на импортированной колоде + `due`/`state` совпадают (закрывает и C6-производственную проводку). ## Что проверено и признано ок

**Домен/данные/транзакции.** `recordReview` пишет `review_logs` и `cards.state/fsrs_json/due/updated_at` в одной `database.transaction` (`drift_review_repository.dart:40-94`); undo — компенсирующая транзакция «удалить лог → восстановить полный снимок карточки» (`:97-114`, `cardToCompanion` восстанавливает все 24 поля, включая `updated_at`); при отсутствии карточки/лога — `StateError` и откат (проверено тестами `:145-209`; полнота отката после первой записи — M1). `ReviewUndo` — только in-memory стек движка (ADR-008). Формула `scheduled_days`/`actual_days` соответствует ADR-008 (проверено `closeTo` в тестах); `elapsed_ms` — от момента показа (`engine:179`).

**FSRS-маппинг.** Единый `CardState` (`domain/cards/card.dart:29-54`, реэкспорт из `scheduling_card.dart:1-3`, дубликат удалён); `new→learning` step 0 при маппинге в пакет (`fsrs_mapper.dart:34-38`), обратно — только learning/review/relearning (`:44-48`, `new` восстанавливается по отсутствию истории); битый/чужой `fsrs_json` → `FormatException`, без тихого сброса (`card_scheduling.dart:19-45`); `previewIntervals` и `review` используют одну операцию `reviewCard` с одинаковым `reviewDateTime` (детерминизм: fuzzing выключен, ADR-004; probe совпал с `fsrs-intervals.md`); `_fromFsrsCard` сохраняет `cardId` исходной карточки. Стык с импортом — H1.

**Очередь.** `ReviewQueue.build` (`review_queue.dart:15-46`): исключены `suspended` и `buriedUntil > now`; входят `due <= now` (не new) и все `new`; порядок — due ASC, затем createdAt ASC, тай-брейк id; будущие due не входят; граница `due == now` покрыта; исходный список не мутируется (тесты `review_queue_test.dart:34-147`). ADR-008 соблюдён.

**UI-каркас A6.4/A7.2.** Линейный прогресс (`ratedCount/total`), undo-иконка с disabled при пустом стеке/busy, диалог выхода (X), «Почему?» (disabled без `source_excerpt`, bottom sheet с цитатой), центр — карточка с flip, низ — 4 кнопки с прогнозом над каждой (`review_interval_format` + ARB), роли цветов A7.2, клавиши 1–4/Space, haptics оценок по A7.2, состояния пусто/завершено/ошибка (ARB, без сырых текстов). Прогресс/undo-счётчик корректно меняются после undo (index-1, revealed=true). Отступления: M2 (back без диалога), M3 (haptics reveal/complete), L5 (косметика).

**Движок/гонки.** `busy` выставляется синхронно до `await`, поэтому повторный `rate/undo` в полёте возвращает `false` (двойной записи нет); при ошибке записи сессия не двигается, `busy` сбрасывается, ошибка пробрасывается в экран → ARB-сообщение (тесты `review_session_engine_test.dart:119-134,158-169`, widget `:166-182`); ошибка undo сохраняет стек и позицию; завершение/пустое состояние корректны. Гонка «запись завершилась после закрытия экрана» закрыта в рабочем дереве `_disposed` (L11 — без теста).
