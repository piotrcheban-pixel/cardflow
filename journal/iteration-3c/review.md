## High

### H1. При нуле карточек UI выбрасывает ошибки фрагментов и показывает «пустой ответ» вместо реальной ошибки и повтора

**Доказательство:**
- `lib/api/generation/generation_pipeline.dart:342-358` — при непустом `failures` и пустых `cards` пайплайн
  штатно возвращает результат со `status = error`, а не бросает исключение;
- `lib/api/generation/generation_pipeline.dart:371-383` — эти `failures` (текст фрагмента, код, limit) есть
  в `GenerationRunResult`;
- `test/unit/api/generation/generation_pipeline_test.dart:343-358` — тест подтверждает такой результат:
  `cards` пуст, `failures` содержит `serverUnavailable`;
- `lib/ui/generation/generation_screen.dart:325-332` — экран смотрит только на `result.cards`: при пустом
  списке показывает `l10n.generationErrorEmptyResponse` и делает `return`, не читая `result.failures` и не
  открывая предпросмотр;
- `lib/l10n/app_ru.arb:663` — это строка «Нейросеть вернула пустой ответ. Попробуйте ещё раз» (не сеть/5xx).

**Почему дефект:** по A6.8 частичный успех должен показывать полученное и ошибки по фрагментам с кнопкой
«Повторить неудавшиеся», а A8.5 шаг 8 требует ошибку фрагмента с возможностью повтора. При падении **всех**
фрагментов (нет сети, 5xx, все фрагменты обрезаны) пользователь получает ложное сообщение «пустой ответ» и
не может повторить упавшие фрагменты; предпросмотр, который умеет показывать `failures` и retry при пустых
карточках (`generation_preview_screen.dart:229-300`), недостижим. Это функциональная ошибка сценария A6.8,
а не только текст.

**Минимальная рекомендация:** при `result.failures.isNotEmpty` открывать предпросмотр и при пустых карточках
(кнопки импорта уже отключены, retry доступен) либо показывать ARB первой ошибки `failures.first.code` и
кнопку повтора. Добавить widget-тест «все фрагменты упали по network → сообщение о сети/повтор, не
`generationErrorEmptyResponse`».

### H2. «Сгенерировать» активна, пока файлы ещё парсятся: часть прикреплённых материалов молча не попадает в запрос

**Доказательство:**
- `lib/ui/generation/generation_screen.dart:209-211` — файлы парсятся последовательно (`await _parse`),
  это асинхронно и при больших файлах занимает заметное время;
- `lib/ui/generation/generation_screen.dart:153-157` — `_parsedDocuments` берёт только файлы со статусом
  `parsed`; файлы в статусе `parsing` игнорируются;
- `lib/ui/generation/generation_screen.dart:263-274` — `_generate` проверяет только `_files.isEmpty` и
  `documents.isEmpty`; проверки «есть ли ещё `parsing`» нет;
- `lib/ui/generation/generation_screen.dart:424-432` — кнопка «Сгенерировать» всё это время активна.

**Почему дефект:** пользователь прикрепляет несколько файлов, сразу нажимает «Сгенерировать», и запрос уходит
только с уже разобранными файлами; оставшиеся не попадают в материалы и не показываются как ошибка. Это
тихая потеря содержания и нарушение A8.5 шаг 3–4 (все прикреплённые файлы должны быть разобраны, ошибки — по
файлу). Отдельный неприятный случай — единственный ещё не разобранный файл: показывается
`generationNoParsedFilesError` «Ни один файл не удалось прочитать», хотя чтение ещё идёт.

**Минимальная рекомендация:** хранить счётчик/признак `parsing` и блокировать `_generate` (или дожидаться
завершения всех парсингов, не смешивая с ошибками), пока есть файлы в статусе `parsing`; обновлять состояние
по завершении. Добавить widget-тест: два файла, первый разобран, второй ещё парсится — генерация не
стартует (или стартует только после завершения).

## Medium

### M1. `retryFailed` жёстко ставит `splitAttempted: true`, из-за чего повтор упавшего фрагмента не может быть раздроблен при `truncated`

**Доказательство:** `lib/api/generation/generation_pipeline.dart:178-187` — для каждого `GenerationChunkFailure`
создаётся `GenerationChunk(..., splitAttempted: true)`; сама ошибка этого признака не хранит. Далее
`generation_pipeline.dart:295-305` дробит только `!chunk.splitAttempted`.

**Почему дефект:** если фрагмент упал по `network`/`rateLimited`, он никогда не дробился. На повторе модель
может вернуть `truncated`, и по A8.5 шаг 8 этот фрагмент ещё имеет право на одно деление — но из-за
жёсткого `true` деление не выполняется, фрагмент сразу снова падает, и пользователь может повторять его
бесконечно без прогресса. Это расхождение с «split-once» и с тестом `generation_pipeline_test.dart:388-435`,
который проверяет только первый проход.

**Минимальная рекомендация:** добавить `splitAttempted` в `GenerationChunkFailure` (или хранить исходный
`GenerationChunk`) и передавать фактическое значение в retry; добавить тест «network-фейл → retry →
truncated → деление один раз».

### M2. Fatal-код после частичного успеха выбрасывает уже полученные карточки

**Доказательство:** `lib/api/generation/generation_pipeline.dart:291-294` — fatal-код (`invalidApiKey` и др.)
делает `break`; `generation_pipeline.dart:342-369` — задание сохраняется как `error` с `cardsCount`, но
результат не возвращается: `throw fatal`; `lib/ui/generation/generation_screen.dart:343-357` ловит
`GenerationException` и показывает сообщение, предпросмотр не открывается.

**Почему дефект:** если первый фрагмент уже дал карточки, а второй (например, из-за отозванного ключа)
дал fatal, пользователь теряет оплаченный результат: карточки есть только в памяти пайплайна, в
`generation_jobs` нет `result_deck_id`, а UI не даёт их посмотреть/импортировать. ADR-015 §3 требует
останавливать пайплайн, но не требует выбрасывать уже полученное; A6.8 говорит о предпросмотре полученного
при частичном успехе.

**Минимальная рекомендация:** при fatal возвращать `GenerationRunResult` с уже принятыми карточками и
fatal-ошибкой (или сохранять их в job и открывать предпросмотр); отдельный тест «первый фрагмент успешен,
второй — invalidApiKey».

### M3. Catch-all вокруг вызова модели захватывает и сохранение job: ошибки БД превращаются в «ошибку фрагмента» с двойным `processed`

**Доказательство:** `lib/api/generation/generation_pipeline.dart:245-279` — `try` включает не только
`caller.generate`, но и приём карточек и `jobRepository.save(...)`; `generation_pipeline.dart:325-338` —
`on Object` добавляет `GenerationChunkFailure(invalidResponse)` и делает `processed++` ещё раз.

**Почему дефект:** при сбое записи в `generation_jobs` (или любом исключении после успешного ответа) уже
принятые карточки остаются в `cards`, но этот же фрагмент одновременно попадает в `failures`; счётчик
`processed`/`chunk_count` увеличивается дважды, пошаговое обновление job теряется. Пользователь увидит
частичный успех с ошибкой фрагмента, который на самом деле succeeded; диагностика БД маскируется под ответ
модели.

**Минимальная рекомендация:** сузить `try` до `caller.generate` (карточки/дедуп — после успешного ответа),
а ошибки `jobRepository.save` считать фатальными для запуска (сохранить `error`/пробросить с ARB), не
смешивая с `invalidResponse`; добавить тест с падающим `GenerationJobRepository.save`.

### M4. Исключение до цикла (например, чтение хешей колоды) оставляет `generation_jobs.status = running` навсегда

**Доказательство:** `lib/api/generation/generation_pipeline.dart:104` — начальное задание `running`
сохраняется до чанкинга/дедупликации; `generation_pipeline.dart:133-135` — `_existingHashes` (запрос к
`cardStore`, то есть к БД) вызывается вне `try`; `lib/ui/generation/generation_screen.dart:354-357` —
неожиданное исключение показывается общим ARB, но job не обновляется.

**Почему дефект:** при ошибке БД/закрытой базе (`existingContentHashes`, `jobRepository.save` начального
задания и т.п.) задание остаётся `running` без `error_code`, хотя генерация не выполнялась; это нарушает
A8.5 шаг 12 и оставляет мусорное состояние для будущего экрана истории/ретраев. Сейчас UI просто показывает
generic-ошибку.

**Минимальная рекомендация:** обернуть `run`/`retryFailed` в `try/catch/finally`, при исключении сохранять
job `error` с машинным кодом (или, как минимум, `cancelled/error`), и вычищать начальное состояние; тест с
падающим `existingContentHashes`.

### M5. Если все карточки оказались дублями, показывается «Нейросеть вернула пустой ответ», хотя модель ответила

**Доказательство:** `lib/api/generation/generation_pipeline.dart:347-348` — при пустом `failures` и пустых
`cards` статус = `done`; `generation_pipeline.dart:375-383` — `duplicatesRemoved` возвращается, карточек нет;
`test/integration/generation_flow_test.dart:154-183` — повторная генерация в ту же колоду даёт
`second.cards.isEmpty`, `second.duplicatesRemoved == 1`, job `done`; `lib/ui/generation/generation_screen.dart:329-332`
— любой пустой `cards` превращается в `generationErrorEmptyResponse`.

**Почему дефект:** при повторной генерации в существующую колоду модель вернула карточки, но они были
отсеяны как дубли. Пользователь видит ложную ошибку «пустой ответ» и не видит ни `duplicatesRemoved`, ни
предпросмотр; это подрывает доверие к A8.5 шаг 9 и A6.8. ARB `generationPreviewEmpty` «Модель не вернула
карточки» в этом случае тоже неточна.

**Минимальная рекомендация:** отдельное пустое состояние/сообщение для `duplicatesRemoved > 0` («Все
карточки уже есть в колоде») и, при желании, предпросмотр без карточек; добавить тест на дубликаты в UI.

### M6. Возврат с экрана настроек сбрасывает выбранные провайдера и модель на значение по умолчанию

**Доказательство:** `lib/ui/generation/generation_screen.dart:119-120` — `_loadProviderConfig` всегда
перезаписывает `_provider = _defaultProvider(...)` и `_modelId = _defaultModelId(...)`;
`generation_screen.dart:258-261` — `_openSettings` вызывает её после каждого возврата с `/settings/generation`.

**Почему дефект:** пользователь выбрал, например, Gemini, у него нет ключа, он ушёл в настройки по баннеру,
сохранил ключ и вернулся — экран выбирает первого провайдера с ключом по порядку OpenAI/Gemini/Anthropic и
сбрасывает модель. Выбор пользователя теряется; если у OpenAI есть ключ, выбор Gemini вообще исчезнет, и
баннер снова не покажет нужный провайдер. Это нарушает A6.8 «Селектор провайдера/модели».

**Минимальная рекомендация:** при повторной загрузке сохранять текущие `_provider` и `_modelId`, если они
всё ещё валидны; `_defaultProvider` применять только при инициализации. Тест: выбрать Gemini → открыть
настройки → вернуться → выбор Gemini и модель Gemini сохранены.

### M7. Ошибка чтения ключей/настроек в `_loadProviderConfig` не перехватывается — экран навсегда остаётся на спиннере

**Доказательство:** `lib/ui/generation/generation_screen.dart:101-122` — нет `try/catch`; `_loading = false`
выставляется только внутри `setState` после всех `await`; при исключении future завершается ошибкой, экран
остаётся с `_loading = true` (`generation_screen.dart:393-395`). Для сравнения
`lib/ui/settings/generation_settings_screen.dart:80-121` ловит ошибку и показывает ARB + «Повторить».

**Почему дефект:** `flutter_secure_storage`/БД могут бросить платформенное исключение (L28); в этом случае
пользователь видит вечный `CircularProgressIndicator`, не может прикрепить файлы или уйти в настройки
осмысленно; нарушен A8.6 (сообщения только ARB, но сообщения вообще нет). Это реальный риск на мобильных
платформах и при недоступном secure storage.

**Минимальная рекомендация:** обернуть загрузку в `try/catch`, выставлять `_loading=false` и показывать
ARB-сообщение с кнопкой «Открыть настройки»/«Повторить»; добавить тест с `FakeApiKeyStore.read`, бросающим
исключение.

### M8. Два разных файла с одинаковым именем считаются одним на платформах без локального пути: второй молча отбрасывается

**Доказательство:** `lib/data/generation/file_picker_document_gateway.dart:53-58` — при отсутствии локального
пути создаётся синтетический `memory://${file.name}`; `lib/ui/generation/generation_screen.dart:198-202` —
дедупликация в `_attach` идёт по `picked.path`. На Android `PlatformFile.path` для SAF-документов обычно
`null` (content://), значит путь синтетический и зависит только от имени; на iOS плагин обычно копирует файл
во временный путь, но контракт `PlatformFile.path` остаётся nullable.

**Почему дефект:** два разных документа `notes.txt` из разных папок (или одноимённые вложения) — обычный
случай; второй файл не добавляется, его материалы не попадают в генерацию, ошибки нет. Нарушен A6.8
«Множественный выбор» и A8.5 шаг 3.

**Минимальная рекомендация:** не использовать имя как идентичность: давать каждому `PickedDocument`
уникальный id/индекс пика или дедуплицировать по байтам/хешу; добавить тест с двумя `preloadedBytes`-
документами одинакового имени.

### M9. При неизвестной длине файла лимит 25 МБ фактически не проверяется до чтения в память

**Доказательство:** `lib/data/generation/file_picker_document_gateway.dart:38-51` — если `lengthSync()` и
`length()` вернули `null`, `size = 0`, условие `size <= maxFileBytes` истинно, и весь файл читается
`file.readAsBytes()` без ограничения; `file_picker_document_gateway.dart:65-73` — `readDocument` для
`preloadedBytes` проверяет только `document.sizeBytes` (то есть тот самый `0`), а не длину массива.
ADR-015 §5 и A8.3 требуют проверку 25 МБ **до** чтения в память.

**Почему дефект:** на платформах/провайдерах, где размер не сообщается, большой файл читается целиком;
это прямой путь к OOM (L25) и нарушение заявленного контракта. L25 уже известное ограничение для реальных
устройств, но здесь код не просто «не проверяет на мобильном», а обходит собственную проверку.

**Минимальная рекомендация:** при неизвестном размере не читать сразу: отклонять с `fileTooLarge`/
`unreadableFile` или читать потоком с подсчётом и остановкой на лимите; после чтения сверять фактическую
длину `preloadedBytes` с `maxFileBytes`. Тест: `lengthSync()/length()` = null, байтов больше лимита.

### M10. Гейт `dart format` красный: один файл итерации не отформатирован

**Доказательство:** `fvm dart format --output=show --set-exit-if-changed lib test` → `exit=1`,
`Formatted 218 files (1 changed)`; локальный bisect `fvm dart format --output=none --set-exit-if-changed lib/ui/generation` → exit 1. Файл:
`lib/ui/generation/generation_preview_screen.dart:378-386` — форматтер ожидает `Text(switch (...) {...},
style: ...)` вместо текущего многострочного `Text(\n switch ...)`; полный diff форматтера — только этот
фрагмент. Формальная причина — `dart format` хочет иное форматирование switch-expression.

**Почему дефект:** AGENTS.md и план C14/задача T22 требуют `dart format` 0 changed; без этого verify-гейт
не проходит и CI/release может быть красным. Это не stylistic nitpick: это формальный критерий приёмки
итерации.

**Минимальная рекомендация:** Lead выполняет `fvm dart format lib test` (пишет файл) и коммитит формат
отдельным `style:`/`fix:`-коммитом; повторный `--set-exit-if-changed` должен быть 0.

### M11. Уход с экрана (системный Back) не отменяет генерацию

**Доказательство:** `lib/ui/generation/generation_screen.dart:93-98` — `dispose` освобождает только
контроллеры; `_cancellation` не отменяется; `generation_screen.dart:381-383` — `cancel()` вызывается только
кнопкой «Отмена». `PopScope`/`WillPopScope` в файле отсутствует.

**Почему дефект:** пользователь может нажать системный Back во время генерации (AppBar/жест): экран
закрывается, а `runner.run` продолжает последовательные запросы, обновляет `generation_jobs` и тратит
токены; вернувшись, пользователь не увидит ни прогресса, ни результата. Это ресурсный и UX-дефект A6.8
(«Отмена» и контроль генерации).

**Минимальная рекомендация:** `PopScope(canPop: !_generating, onPopInvokedWithResult: ...)` с диалогом
«Отменить генерацию?» и вызовом `_cancellation?.cancel()`; либо отменять в `dispose`. Тест: Back во время
`pending` → токен отменён.

### M12. Бюджет fallback для модели вне каталога даёт 2000 токенов вместо заявленных 8000

**Доказательство:** `lib/domain/generation/generation_model.dart:17-18` — `kFallbackInputTokenBudget = 8000`
с комментарием «Бюджет входа, если модель не найдена в каталоге»; `generation_model.dart:133-140` — эта
константа используется как `contextTokens` и из неё вычитаются `8192` (резерв ответа), промпт и `512`; в
итоге отрицательное значение поднимается до `kMinInputTokenBudget = 2000`. ADR-015 §1: «если модель не
найдена, используется консервативный бюджет 8000».

**Почему дефект:** это прямое расхождение с ADR и фактическая ошибка бюджета: неизвестная модель получает
вчетверо меньший фрагмент (лишние запросы/стоимость). Сейчас UI предлагает только модели каталога и
неизвестную облачную модель выбрать нельзя, поэтому путь латентный; но контракт функции и будущие модели
(или удаление модели из каталога) ломаются молча.

**Минимальная рекомендация:** вернуть `kFallbackInputTokenBudget` напрямую для `model == null` (не
вычитать резерв ответа из него) или хранить это как context и явно документировать; тест
`inputTokenBudget(provider: openai, modelId: 'нет', ...) == 8000`.

## Low

### L1. Оценка «Примерно N токенов» не учитывает системный промпт, обёртку и оценку выхода (расхождение с ADR-015 §1)

**Доказательство:** `lib/ui/generation/generation_screen.dart:159-161` — оценка только по `document.text`;
`lib/api/generation/generation_pipeline.dart:128-132` — пайплайн добавляет системный промпт и wrapper, но
тоже без оценки выхода по `<limit>`; ADR-015 §1, строки 49–50: «Примерно N токенов» = оценка входных
токенов + оценка выхода по `<limit>`; порог 100 000 входных токенов. **Почему:** пользователь видит
заниженную оценку (на один/несколько промптов и выход), а предупреждение срабатывает только по материалу.
**Рекомендация:** общий оценщик для UI/пайплайна: материалы + системный промпт + wrapper + оценочный выход
по limit; тест, что UI-оценка > суммы материалов.

### L2. DnD-файлы показываются без размера (A6.8 требует имя, размер, статус)

**Доказательство:** `lib/ui/generation/generation_screen.dart:185-189` — `sizeBytes: 0` для DropItem;
`generation_screen.dart:694-696` — размер скрывается при `sizeBytes <= 0`. **Почему:** для перетащенных
файлов список не показывает размер, хотя A6.8 и C3 его требуют; также до чтения нельзя показать пользователю
файл больше 25 МБ. **Рекомендация:** получать `File(item.path).lengthSync()` (с обработкой ошибки) или
обновлять `sizeBytes` после чтения; добавить widget-тест DnD.

### L3. `_pickFiles` не проверяет `mounted` после системного пикера

**Доказательство:** `lib/ui/generation/generation_screen.dart:163-168` — после `await pickDocuments()` сразу
`await _attach(picked)`; `_attach` вызывает `setState` (`:208`), не проверяя `mounted`. **Почему:** если
пользователь ушёл с экрана, пока открыт системный пикер, по возвращении виджет уже `dispose`, и
`setState` бросит «setState() called after dispose». **Рекомендация:** `if (!mounted) return;` после
`await`; тест с задержанным `FakeDocumentGateway.pickDocuments` и удалением экрана.

### L4. `splitInHalf` режет по UTF-16-индексу и может разрезать surrogate pair

**Доказательство:** `lib/domain/generation/generation_chunker.dart:147-163` — `middle = text.length ~/ 2`,
`substring(0, splitAt)`/`substring(splitAt)`; проверка длины идёт по `runes.length`, но само деление — по
code units. **Почему:** для текста с эмодзи/суррогатными символами на границе середина может разрезать
пару; в запрос уйдут непарные суррогаты (искажение/ошибка JSON). Для русского текста редко, но это
корректность. **Рекомендация:** искать split point по списку runes и склеивать через
`String.fromCharCodes`; тест с парой суррогатов в середине.

### L5. Импорт перезаписывает `generation_jobs.cards_count` числом выбранных/принятых карточек, а не «получено»

**Доказательство:** `lib/data/generation/drift_generation_card_store.dart:110-117` — `cardsCount:
Value<int>(accepted.length)` в транзакции импорта; `lib/data/db/tables.dart:251-252` — комментарий A5:
«Сколько карточек получено». **Почему:** если пользователь импортирует выбранные карточки, job теряет
исходное число полученных (и `skippedDuplicates` не сохраняется); для аудита A8.5 шаг 12 данные неполные.
**Рекомендация:** хранить `imported_count` отдельно или не уменьшать `cards_count`; зафиксировать семантику
в ADR/тесте.

### L6. Сообщение валидации предпросмотра говорит только о пустом вопросе, хотя проверяются ещё ответ, длина и теги

**Доказательство:** `lib/ui/generation/generation_preview_screen.dart:169-182` — `CardDraft.isValid` проверяет
front/back/длины/tags; `lib/l10n/app_ru.arb:1000` — текст «Проверьте заполнение выбранных карточек: вопрос
не должен быть пустым». **Почему:** пользователь, у которого ответ пуст или превышает 2000 символов,
получает неверную подсказку. **Рекомендация:** нейтральный ARB («Проверьте заполнение выбранных карточек»)
или поле-специфичные сообщения.

### L7. Тесты red-фазы менялись в green-фазе без ADR/обновления журнала

**Доказательство:** `git diff 475651c..HEAD -- test/unit/api/generation/generation_pipeline_test.dart`:
`expect(caller.calls, 2)` → `3` для truncated; `test/unit/domain/generation/generation_chunker_test.dart`:
проверка «первый/последний чанк» заменена на `indexWhere`; `journal/iteration-3c/red-generation.md:69`
фиксирует ожидание 2 вызовов. **Почему:** AGENTS/план называют red-тесты неизменяемым контрактом; фактические
ожидания были изменены в зелёной фазе. Для truncated 3 вызова — правильное поведение (оригинал + две
половины), но это должно быть отражено в red-журнале/ADR, а не молчаливой правкой. **Рекомендация:**
обновить red-generation.md и/или добавить пометку в ADR-015; тесты оставить.

### L8. Вход «Сгенерировать карточки» с экрана «Колода» — пункт overflow-меню, а не Toolbar A6.3

**Доказательство:** `lib/ui/decks/deck_screen.dart:59-66` — `PopupMenuItem(value: generate)`; SPEC A6.3,
строка 303: «Toolbar: «Сгенерировать карточки» | Экран API-генерации». **Почему:** это отклонение от SPEC
по discoverability; Plan T17 сознательно говорит «пункт в меню действий», но ADR такого отклонения нет.
**Рекомендация:** либо добавить toolbar-кнопку/пункт по A6.3, либо зафиксировать осознанное отклонение в
ADR и verify; для текущей итерации это low (функция доступна).

### L9. Гонка retry ↔ import в предпросмотре

**Доказательство:** `lib/ui/generation/generation_preview_screen.dart:127-130` — `_retrying` не проверяет
`_importing`; `generation_preview_screen.dart:159-164` — `_importing` не проверяет `_retrying`; кнопки
импорта (`:310-330`) и retry (`:295-299`) блокируются только своими флагами. **Почему:** пользователь
может нажать retry, затем import: импорт зафиксирует старый набор и закроет экран, а retry обновит job уже
после; новые карточки не импортируются, состояние задания и UI расходятся. **Рекомендация:** блокировать
импорт на время retry и наоборот (или объединить в один busy-флаг); тест.

### L10. Тестовые пробелы, которые прямо скрывают H1/H2 и часть M

**Доказательство/пробелы:**

### L11. Мелочь локализации: «1 токенов» и предупреждение о разбиении при 1M-контексте

## Остаточные ограничения

- Живые OpenAI/Gemini/Anthropic не проверялись (L1); DeepSeek success-путь — только 3b/L30. Негативные
  live-контракты 401/403/429/`Retry-After` — ADR-014.
- Реальные файлы с устройств, OOM на 25 МБ, платформенный secure storage — L23/L25/L28; Android/iOS-сборки
  на этом хосте недоступны.
- `fvm flutter build windows --release`, golden-тесты и измерение покрытия в этой сессии не запускались;
  покрытие ≥80% не подтверждено (C14 проверяется на verify).
- Каталог моделей статический (ADR-015); имена моделей могут устареть без изменения контрактов.
- `generation_jobs` не имеет UI истории/resume: после fatal/отмены/ухода с экрана полученные карточки
  недоступны (M2/M11).
- `source_doc_id`/`source_file` для сгенерированных карточек не сохраняются (в A5 есть `source_docs`);
  «Почему?» работает только через `source_excerpt`, если он прошёл проверку A8.4.
- `importGeneratedCards` при отсутствии job-строки молча не обновляет `result_deck_id` (update 0 rows);
  UI-путь не проверен.
- Оценка токенов — эвристика, не токенизатор модели; фактический расход — из `usage`.
