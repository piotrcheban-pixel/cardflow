# ADR-018 — Конструктор сессии: конфиг, фильтры, порядок, пресеты, лимит времени

**Дата:** 2026-11-14 · **Итерация:** 6 · **Статус:** принято
**Контекст SPEC:** A6.7 (экран «Конструктор сессии»), A7.20 (порядок сборки), A7.19 (интерливинг,
разминка), A6.3 (лист режимов), A5 (`session_presets`, `review_logs`), ADR-008 (классическая очередь),
ADR-016 (лента), ADR-005 (схема БД/миграции), ADR-002 (Riverpod).

## Контекст

SPEC задаёт экран и последовательность «колоды → фильтр → режим → лимит → перемешать / интерливинг /
разминка → пресет → начать», но не фиксирует: (1) семантику фильтров (ИЛИ/И, что значит «состояние»);
(2) точный состав и порядок выборки, особенно карточек с будущим `due`; (3) что такое «разминка —
первые 3–5 самые лёгкие»; (4) как передавать готовую выборку в классику и ленту, которые строят очередь
из `ReviewQueue` (ADR-008) и отбрасывают будущие `due`; (5) как исполняется лимит «N минут»;
(6) формат `session_presets.config_json` — колонка в схеме есть (schemaVersion = 1, ADR-005), но
контракта значения нет; (7) что считается «пиявками» в фильтре, если режим пиявок — post-MVP (A7.17).

## Варианты

1. **План сессии строится доменом, движки получают готовый порядок.** `SessionBuilder` (чистая функция:
   фильтры → базовый порядок → разминка → интерливинг → перемешивание → лимит) отдаёт список карточек;
   экран передаёт его сессии через `SessionPlan`; движки классики и ленты принимают флаг «очередь уже
   собрана» и не пересобирают её. Лимит минут — бюджет времени экрана сессии.
   Плюс: порядок предсказуем и тестируем без БД; проверенные движки не меняют поведение при
   `prebuilt = false`; лимит минут не протекает в FSRS-логику. Минус: план живёт в памяти навигации,
   при перезапуске приложения сессия не восстанавливается (как и в итерациях 2/4 — сессии не
   сохраняются).
2. **Расширить `ReviewQueue` параметрами конструктора.** Одна функция на все случаи, движки вызывают её
   с конфигом. Плюс: меньше сущностей. Минус: `ReviewQueue` — контракт классики (ADR-008) и ленты
   (ADR-016); флаги перемешивания/разминки в нём меняют поведение 1020 тестов и двух движков; лимит
   минут в очередь не помещается.
3. **Сохранять собранный план в БД (`session_presets`/новая таблица) и восстанавливать сессию.**
   Плюс: восстановление после перезапуска. Минус: SPEC этого не требует, схема БД после релиза
   меняется только владельцем (`docs/agent-prompt.md` п. 5) — отклонено.

Принимаем **вариант 1**.

## Решение

### 1. Конфиг сессии (`lib/domain/session/session_config.dart`)

Неизменяемый `SessionConfig`:

- `deckIds` — выбранные колоды, **непустой** список (без колод сессии нет; UI не даёт начать);
- `tags` — множество тегов; **пусто = без фильтра**, иначе карточка проходит, если содержит **любой**
  выбранный тег (OR) — чипы-фильтры ведут себя как «или»;
- `cardTypes` — множество `CardType`; пусто = все; иначе **любой** из выбранных;
- `states` — множество `SessionStateFilter`; пусто = все; иначе **любой**:
  `newCards` → `state = new`; `inProgress` → `learning | relearning`; `review` → `state = review`
  («повторение»); `leeches` → ≥8 провалов по `review_logs.rating = 1` (правило A7.17, сам режим
  пиявок остаётся post-MVP);
- `mode` — `classic | feed` (значения совпадают с `review_logs.mode`, ADR-008/016);
- `limit` — `SessionLimit(kind: cards|minutes, value)`: карточки 1…500, минуты 1…180 (по умолчанию
  20 карточек);
- `shuffle`, `interleave`, `warmup` — по умолчанию `false`;
- JSON `{"version": 1, ...}` — контракт `session_presets.config_json`; неизвестные `version` и
  невалидные значения → `FormatException`, пресет пропускается (не ломает список).

Приостановленные (`suspended`) и отложенные (`buriedUntil > now`) карточки в выборку не попадают
никогда — как в ADR-008.

### 2. Сборка выборки (`lib/domain/session/session_builder.dart`, чистая функция)

Порядок операций:

1. **Фильтры** по колодам/тегам/типам/состояниям (см. §1), без `suspended`/`buried`.
2. **Базовый порядок:** `due ASC` (без `due` — в конце), затем `createdAt ASC`, затем `id ASC` —
   детерминизм тестов и то же правило, что ADR-008.
3. **Разминка** (если `warmup`): до 4 карточек в состоянии `review` (уже выучены) с наибольшим
   FSRS-`stability`; при равных — `due ASC`, затем `id ASC`. Переносятся в начало. Битый `fsrs_json`
   не роняет сборку: карточка считается «не лёгкой». Меньше 4 — сколько есть; ни одной — порядок
   не меняется. 4 (а не 5) — середина диапазона «3–5» A7.19.
4. **Перемешивание** (если `shuffle`): остаток после разминки тасуется `Random(seed)` (Fisher–Yates);
   при заданном seed результат детерминирован (тесты), production seed — `DateTime.now().microsecondsSinceEpoch`.
   Префикс разминки не перемешивается: «разминка» остаётся разминкой.
5. **Интерливинг** (если `interleave` и в остатке ≥2 колод): остаток перемешивается round-robin по колодам
   (внутри колоды порядок сохраняется). Выполняется **после** перемешивания: иначе случайный порядок
   снова смешал бы колоды и чередование перестало бы работать. Это даёт ≈50/50; настраиваемые доли
   (70/30) SPEC A7.19 относит к расширенным вариантам — post-MVP.
6. **Лимит:** при `limit.kind = cards` — первые N; при `minutes` — карточки не режутся, вместо этого
   у плана появляется `timeBudget = N минут`.

### 3. План (`lib/domain/session/session_plan.dart`)

`SessionPlan { List<Card> cards; Duration? timeBudget; }` — готовый порядок и бюджет времени.
План передаётся экранам сессий через `GoRouter.extra` (маршруты `/session/classic`, `/session/feed`).
Пустой план к запуску не предлагается: кнопка «Начать сессию» активна только при ≥1 доступной карточке.

### 4. Движки

`ReviewSessionEngine` и `FeedSessionEngine` получают флаг `prebuilt`: при `true` список карточек уже
отфильтрован и упорядочен конструктором и **не** пересобирается `ReviewQueue` (иначе фильтр
«Повторение» терял бы будущие `due`). При `false` (экран колоды, ADR-008/016) поведение не меняется.
Запись оценок, undo, режимы `classic`/`feed` — без изменений (SPEC A5).

### 5. Лимит времени

`timeBudget` исполняется экраном сессии: `Timer` на бюджет, по истечении сессия показывает итоговый
экран «Время сессии истекло» и больше не принимает оценки; карточки, которые не успели, остаются на
следующий раз (их `due`/`fsrs_json` не тронуты). Таймер не переживает перезапуск приложения и
останавливается, пока приложение в фоне — известное ограничение (L40).

### 6. Пресеты (`session_presets`)

`SessionPreset { id, name, config, createdAt }`; id — uuid v4 (как `decks`/`review_logs`).
Порт `SessionPresetRepository` (`presets`, `savePreset`, `deletePreset`), drift-реализация над уже
существующей таблицей. Схема БД, `schemaVersion` и формат `.zip` не меняются (ADR-005, ADR-006).

### 7. Пиявки в фильтре

Счётчик провалов — отдельный порт `LeechRepository.failureCounts(deckIds)` (`review_logs.rating = 1`,
`COUNT` по карточкам). Порог — константа домена `leechFailureThreshold = 8` (A7.17). Это фильтр, а не
режим: экран пиявок/предложений (A7.17) остаётся post-MVP.

### 8. Вне итерации

Экран настроек и статистики (A6.5/A6.6), «Тренировать» из слабых тем (A6.5 — итерация 7),
доли интерливинга/теги в разминке/автонастройка (A7.19 post-MVP), режим пиявок (A7.17),
восстановление сессии после перезапуска, requeue (L20).

## Последствия

- Порядок сессии конструктора детерминирован и покрыт unit-тестами без БД; движки классики и ленты
  повторно используют проверенную логику записи (транзакция на оценку, undo).
- План живёт только в памяти навигации: перезапуск приложения во время сессии её теряет — то же
  поведение, что в итерациях 2/4, фиксируется в `KNOWN_LIMITATIONS.md`.
- Лимит минут не влияет на FSRS-состояние: непройденные карточки остаются как были.
- `session_presets` впервые используется по назначению; миграций не требуется.
- Фильтр «Пиявки» опирается на порог A7.17; при появлении настраиваемого порога (post-MVP) меняется
  одна константа.
