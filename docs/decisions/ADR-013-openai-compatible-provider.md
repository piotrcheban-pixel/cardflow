# ADR-013 — Провайдер «OpenAI-совместимый»: адрес и модель в настройках, ключ — в secure storage

**Дата:** 2026-11-13 · **Статус:** принято (решение владельца) · **Связано:** SPEC A8.2, A8.4, A8.5, A8.6,
A6.6, 3.4; ADR-011; ADR-012; `docs/api-schema.md`; `docs/openai-compatible.md`;
`journal/KNOWN_LIMITATIONS.md` L30

## Контекст

SPEC A8.2 перечисляет три провайдера — OpenAI, Gemini, Anthropic — и не содержит OpenAI-совместимого
сервера. Владелец принял решение добавить четвёртый провайдер: пользователь сам указывает адрес сервера,
модель и, при необходимости, ключ. Это даёт доступ к облачному DeepSeek (https) и локальным Ollama /
LM Studio (localhost, http), а также к любому другому серверу с Chat Completions API. Добавление
провайдера, которого нет в SPEC, — исключительное решение владельца (`docs/agent-prompt.md` §5), поэтому
оформлено ADR.

Ограничения, которые нельзя нарушить:

- **3.4 / A8.6:** ключи API — только `flutter_secure_storage`; в БД, логах, экспорте и `generation_jobs`
  их нет.
- **A8.4:** ответ модели проходит ту же каноническую схему и тот же локальный валидатор; отдельной схемы
  для нового провайдера нет.
- **A8.2 / ADR-011:** строгий режим не гарантирует валидный JSON; причина остановки проверяется.
- **ADR-012:** ретраи, таймауты и редактирование логов — общий транспорт; 400/401/403 не повторяются.
- **3.1:** интерфейс только на русском, латиница — лишь бренды и имена форматов; поэтому экран называется
  «Настройки генерации», а не «API».

Формулировка владельца «адрес, модель и api_key из настроек» уточняется осознанно: адрес и модель —
пользовательские настройки в `app_settings`; ключ — тоже настройка пользователя, но хранится только в
secure storage (`ApiKeyStore`), потому что правило 3.4 запрещает ключи в БД. Это не ослабление требования:
ключ остаётся пользовательским, но в таблицу настроек и БД не попадает.

## Варианты

1. **Отдельные провайдеры под DeepSeek / Ollama / LM Studio** — дублирование адаптеров, UI и настроек;
   каждый новый сервис требует нового ADR и правок кода, хотя протокол у всех один.
2. **Настраиваемый `base_url` в существующем провайдере `openai`** — меняет поведение рабочего провайдера
   (URL, ключ, `generation_jobs.provider`), ломает эталонные тесты и смешивает «OpenAI» с «моим сервером»;
   владелец решил добавить отдельного провайдера.
3. **Пресеты известных сервисов без произвольного адреса** — список совместимых серверов не конечен,
   требование владельца — любой совместимый сервер; отказ.
4. **Отдельный провайдер `openaiCompatible` + один адаптер Chat Completions с настраиваемым
   адресом/моделью/опциональным ключом** (выбран).

## Решение

### 1. Провайдер и имя в данных

`GenerationProvider.openaiCompatible`, `wireName = 'openai_compatible'`
(`lib/domain/generation/generation_provider.dart`). Тот же `wireName` используется в
`generation_jobs.provider` и в настройках. Существующие `openai` / `gemini` / `anthropic` не меняют
поведение: их адаптеры, эталонные ответы и тесты остаются как есть; новый провайдер — дополнительный,
а не замена.

Поддерживаемые сервисы (примеры, список не закрытый): **DeepSeek** — `https://api.deepseek.com`,
**Ollama** — `http://localhost:11434/v1`, **LM Studio** — `http://localhost:1234/v1`, а также любой другой
сервер с Chat Completions API. Пошаговая настройка — `docs/openai-compatible.md`.

### 2. Что где хранится

| Данные | Где | Формат |
|---|---|---|
| `base_url` (корень API) и `model` | `app_settings`, ключ `generation.openai_compatible` | JSON `{"baseUrl": "…", "model": "…"}` (`OpenAiCompatibleSettings`, `lib/data/generation/drift_generation_settings_store.dart`) |
| ключ API (необязателен) | `flutter_secure_storage` через `ApiKeyStore` | ключ хранилища `cardflow.api_key.openai_compatible` |

- Пустые/отсутствующие адрес или модель — состояние «сервер не настроен»
  (`OpenAiCompatibleSettings.isConfigured == false`); ошибка `providerNotConfigured`, запрос в сеть
  не выполняется.
- Имя модели для этого провайдера берётся из настроек: списка моделей нет, сохранённая модель — источник
  истины для запроса (в отличие от трёх встроенных провайдеров, где модель — параметр вызова).
- **Один активный совместимый сервер:** одна пара адрес+модель. Профили нескольких серверов — post-MVP,
  в MVP не вводятся.
- Повреждённое JSON-значение в `app_settings` не роняет экран и генерацию — трактуется как «не настроено»,
  пользователь настраивает заново.
- Ключ в `app_settings` не хранится вообще (полей нет) — прямое следствие 3.4 и guard-теста `no_secrets`.

### 3. Адрес и сборка эндпоинта

- Проверка `base_url`: схемы — только `http`/`https`. `https` рекомендован для облачных серверов, `http` —
  для локальных и доверенных (локальная сеть, самодельный сервер); жёсткого запрета `http` нет. Передача
  ключа по `http` — риск на стороне пользователя (канал не шифруется, адрес виден в настройках) и
  фиксируется как ограничение (§12). `userinfo` (`user:password@`), query и fragment запрещены: ключи и
  параметры — не в URL (A8.6; редактирование логов не ослабляет правило). Путь сохраняется — `/v1`
  является частью API-корня Ollama и LM Studio.
- Хвостовой `/` нормализуется: двойного слэша не возникает. Сборка и проверка адреса —
  `OpenAiCompatibleEndpoint.parse` (`lib/api/providers/openai_compatible_endpoint.dart`), адаптер —
  `lib/api/providers/openai_compatible_adapter.dart`.
- Эндпоинт — **`base_url + /chat/completions`**: `https://api.deepseek.com/chat/completions`,
  `http://localhost:11434/v1/chat/completions`, `http://localhost:1234/v1/chat/completions`. Путь
  дописывается приложением ровно один раз: полный адрес эндпоинта второй раз не добавляется (пользователь
  вводит корень API, а не готовый URL).
- Заголовок `Authorization: Bearer <key>` отправляется только если ключ задан. Пустой/отсутствующий ключ —
  заголовка нет (локальные серверы обычно без аутентификации).

### 4. Запрос: строгая схема и один fallback

Тело запроса — как у OpenAI-адаптера (ADR-011 §3): `model`, `messages` (`system`+`user`), `response_format`
со strict-схемой канона A8.4 (`json_schema {name: "cards_response", strict: true, schema: …}`). Лимит
токенов ответа не передаётся: ограничение — `<limit>` карточек, обрезание распознаётся по `finish_reason`
(как у OpenAI, ADR-011 §3).

**Fallback — осознанное отступление от «только strict»:** не все совместимые серверы поддерживают
`response_format` со `json_schema` (особенно локальные). Порядок:

1. первый запрос — строгий, как у OpenAI;
2. при **любой** ошибке кода `badRequest` (все 4xx, кроме 401/403/429: 400, 404, 422 и т.п.) — **ровно
   один** повтор того же запроса без `response_format` (тот же промпт, та же модель, те же сообщения);
3. ответ в обоих случаях проходит одну и ту же локальную валидацию канонической схемы A8.4
   (`CardResponseSchema`) и контентные правила — послаблений нет;
4. JSON, обёрнутый в markdown-ограждение (тройные обратные кавычки, в том числе с меткой json) или
   окружённый пояснительным текстом, извлекается до декодирования — так локальные модели иногда отвечают
   и без `response_format`; у остальных провайдеров ответ обязан быть чистым JSON;
5. fallback — **не** ретрай политики ADR-012: 4xx не повторяются транспортом; это осознанный второй
   запрос другой формы, один раз. При 401/403/429/5xx/таймауте fallback не выполняется — работают обычные
   коды ошибок и ретраи ADR-012.

Если и после fallback ответ невалиден по схеме — `invalidResponse`: карточки фрагмента не импортируются
(A8.4).

### 5. Разбор ответа

Как у OpenAI (ADR-011 §3): `choices[0].message.content` — строка; пустой/`null` → `emptyResponse`;
`message.refusal != null` → `refused`; `finish_reason == "length"` → `truncated`; не JSON или нарушение
схемы → `invalidResponse`; `usage.prompt_tokens/completion_tokens/total_tokens` → `TokenUsage`. Адаптер
приводит ответ к общему контракту `GenerationProviderAdapter`, сервис не разбирает провайдерные
особенности.

### 6. Настройки в интерфейсе

- Экран — **«Настройки генерации»** (не «API»: «API» — не бренд, правило 3.1); блок провайдера —
  «OpenAI-совместимый сервер».
- Поля: «Адрес сервера», «Модель», «Ключ доступа (необязательно)». Списка моделей у произвольного сервера
  нет — модель вводится вручную; подсказки по адресу и модели для DeepSeek / Ollama / LM Studio —
  в `docs/openai-compatible.md`.
- Сохранение: адрес и модель → `GenerationSettingsStore` (`app_settings`), ключ → `ApiKeyStore`.
  Сохранённый ключ не показывается: новый ключ заменяет старый, пустое поле при сохранении удаляет ключ
  (для локальных серверов это нормальное состояние). Проверка ключа A6.6 использует те же слои (отдельная
  задача); мёртвых кнопок не появляется.
- Валидация адреса выполняется до запроса, сообщения — только из ARB («Укажите адрес сервера»,
  «Проверьте адрес: нужен полный адрес с протоколом», «Укажите модель»); невалидный/пустой адрес в сеть
  не отправляется (код `providerNotConfigured`).
- В селекторе провайдеров «OpenAI-совместимый сервер» — четвёртый вариант; без настроек генерация просит
  указать адрес и модель, а не падает.

### 7. Ошибки и сообщения

Новый, 13-й код `GenerationErrorCode` — **`providerNotConfigured`**. Сообщение UI: **«Сервер не настроен.
Укажите адрес и модель в настройках»** (строка ARB). Причина — пустые или некорректные адрес/модель
совместимого сервера; запрос в сеть не выполняется, повторов нет.

Остальные ошибки — существующие коды ADR-011 §5: `invalidApiKey` (401/403), `badRequest` (400/404/422 и
прочие 4xx, в том числе после отклонённого fallback), `rateLimited`, `serverUnavailable`, `timeout`,
`network`, `cancelled`, `emptyResponse`, `truncated`, `refused`, `invalidResponse`. Пользователю — только
строки ARB; сырые ответы сервера и `details` не показываются.

### 8. Безопасность

- Ключ — только `ApiKeyStore` (secure storage): в `app_settings`, БД, логах, экспорте и `generation_jobs`
  его нет.
- `Authorization` редактируется существующим `RedactingLogInterceptor` (ADR-012 §3); тела запросов и
  ответов не логируются вовсе — материалы и ответ модели остаются вне логов.
- `base_url` — не секрет, но из него вычищаются `userinfo`/query/fragment (см. §3): ключ в URL не
  поддерживается by design.
- `http` не запрещён: он нужен для локальных и доверенных серверов, `https` рекомендован и ожидается для
  облачных. Передача ключа по `http` — риск на стороне пользователя (ключ и материалы идут по каналу
  открытым текстом); жёсткой проверки localhost нет — это осознанное ограничение (§12). Локальный сервер
  получает материалы пользователя по его выбору: данные не уходят третьим лицам, но уходят в указанную
  службу.
- Android Auto Backup исключён (ADR-012 §4) — ключ совместимого провайдера защищён тем же механизмом.

### 9. Live-проверка

**Статус: ожидает ключ, фиксируется в `journal/KNOWN_LIMITATIONS.md` (L30). «Проверено» не заявляется,
пока live-прогон не подтверждён.**

На момент принятия ADR: ключа DeepSeek в окружении нет (`DEEPSEEK_API_KEY` отсутствует), локальные Ollama
и LM Studio не подняты — живые вызовы не выполнялись. Что должно быть проверено (тег `live`; без ключа —
skip):

- DeepSeek: `DEEPSEEK_API_KEY`; `DEEPSEEK_BASE_URL` по умолчанию `https://api.deepseek.com`;
  `DEEPSEEK_MODEL` по умолчанию `deepseek-chat`. Ожидается срабатывание fallback, если сервис не принимает
  `response_format` со strict-схемой; фактический код ответа и путь фиксируются в результате.
- Ollama (`http://localhost:11434/v1`) и LM Studio (`http://localhost:1234/v1`) — без ключа; в этой среде
  серверы не запущены.
- Проверяется: сборка URL без двойного пути, отсутствие `Authorization` без ключа, fallback ровно один раз,
  извлечение JSON из markdown-ограждения и текста вокруг него, маппинг причин остановки, редактирование
  `Authorization` в логах.

**Результат:** (заполняется после live-прогона; сейчас — нет).

### 10. Что не меняется

- Каноническая схема A8.4 и локальный валидатор — те же.
- Три существующих провайдера и их контракты — без изменений; их тесты остаются эталоном.
- Промпт `gen-ru-v2` — тот же; версия пишется в `generation_jobs.prompt_version`.
- Транспорт, ретраи, таймауты и редактирование логов (ADR-012) — общие, без правок.
- `generation_jobs.provider` принимает `openai_compatible`; миграции схемы не требуются (поле — текст).

### 11. Production-проводка

`lib/ui/state/app_providers.dart`: `generationSettingsStoreProvider` (`DriftGenerationSettingsStore`),
`openAiCompatibleSettingsProvider` (FutureProvider для экрана настроек), `generationAdapters` с
`OpenAiCompatibleAdapter()`, `cardGenerationServiceProvider` получает `generationSettingsStore`.
Интеграционный тест проверяет живой граф с fake-транспортом и fake-хранилищами (урок H1 итерации 2: слой
подтверждается на production-проводке).

### 12. Ограничения

- Строгий `response_format` поддерживают не все совместимые серверы; выручает один fallback без
  `response_format` с локальной валидацией канонической схемы (§4).
- Ответ может прийти в markdown-ограждении или с пояснительным текстом — JSON извлекается, но схема
  проверяется строго (§4).
- Списка моделей нет: имя модели вводится вручную; ошибка в имени — `badRequest` после запроса.
- Один активный совместимый сервер; профили нескольких серверов — post-MVP.
- `http` разрешён для любого хоста (локальная сеть, самодельные серверы): `https` рекомендован для
  облачных, ключ по `http` — риск на стороне пользователя, жёсткого запрета нет (§3, §8).
- Ключ необязателен: локальные серверы обычно работают без аутентификации (§3).
- Доступность и качество сервера — ответственность пользователя; CardFlow не проверяет сервер заранее.
- Живые контракты DeepSeek/Ollama/LM Studio не проверены (L30, §9).

## Последствия

- Один адаптер Chat Completions покрывает DeepSeek, Ollama, LM Studio и любой совместимый сервер: новые
  сервисы не требуют новых провайдеров и новых ADR.
- Fallback сохраняет строгий путь для серверов, которые его умеют, и даёт работать локальным — ценой
  второго запроса только при `badRequest` (4xx); карточки без валидной схемы не принимаются ни в одном из
  путей.
- `GenerationErrorCode` расширен до 13 кодов; при пустых настройках пользователь видит «Сервер не
  настроен…», а не сетевую ошибку.
- Списка моделей нет: ошибка в имени модели возвращается как `badRequest`/`providerNotConfigured` и
  исправляется в настройках, а не в селекторе.
- Пользователь сам отвечает за доступность и качество своего сервера и за то, куда уходят материалы
  (адрес виден в настройках).
- Живые контракты не проверены (L30): до появления ключа поведение подтверждается эталонными ответами и
  fake-транспортом; результат live-прогона дополняет §9.
- Профили нескольких серверов, автоподбор адреса/модели и список моделей — post-MVP; при необходимости —
  новый ADR.
