# ADR-014 — Границы live-проверки провайдеров: success-путь DeepSeek закрыт, живые ошибки не проверяются

**Дата:** 2026-11-14 · **Статус:** принято (решение владельца) · **Связано:** SPEC A8.2, A8.5;
ADR-011; ADR-012; ADR-013; `journal/KNOWN_LIMITATIONS.md` L1, L30, L32;
`journal/iteration-3b/live-l30.md`

## Контекст

**2026-11-14 живьём проверен success-путь DeepSeek:** `fvm flutter test test/live --tags live` → 1 passed
(`deepseek-chat`, 3 карточки, 1231 токен) — подтверждены живой `POST /chat/completions`,
Bearer-аутентификация, разбор ответа, локальная валидация канонической схемы A8.4 и контентные правила.
Детали — `journal/iteration-3b/live-l30.md`.

После этого прогона у L30 оставались непроверенными живые негативные контракты: 401/403 (`invalidApiKey`),
429 и `Retry-After`, `truncated`/`refused`, таймауты. В отчёте был предложен отдельный шаг — подставить
заведомо неверный ключ и/или создать нагрузку, чтобы увидеть реальные коды и заголовки.

Владелец решил: **живьём 401/429/`Retry-After` не проверять — success-пути DeepSeek достаточно, остаток
L30 остаётся известным ограничением.** Решение владельца (не «не успели»), поэтому фиксируется ADR.

## Варианты

1. **Проверять живьём негативные пути** — подставлять неверный ключ, генерировать 429/таймауты. Даёт живые
   коды и заголовки, но требует согласованного способа, рискует временной блокировкой/лимитами на стороне
   провайдера, недетерминирован (429 зависит от нагрузки) и не годится для CI.
2. **Не проверять негативные пути живьём; доверять общему транспорту и unit/fake-тестам** (выбран).
3. **Выделенный тестовый ключ/аккаунт провайдера** — избыточно для MVP и требует ресурсов владельца.

## Решение

1. **Обязательная live-проверка = success-путь DeepSeek** — она уже есть и пройдена (ADR-013 §9,
   `test/live/openai_compatible_deepseek_live_test.dart`; тег `live`, self-skip без ключа; на CI ключа нет,
   тест пропускается).
2. **Живые 401/403/429, `Retry-After`, `truncated`/`refused` и таймауты на реальном API не проверяются** —
   осознанно. Их поведение подтверждается unit- и integration-тестами на fake-транспорте:
   `retry_policy_test.dart` (429 `Retry-After` — секунды и HTTP-date, 5xx/таймауты, 4xx без повторов, отмена),
   `generation_http_client_test.dart`, тесты адаптеров (`truncated`/`refused`/`emptyResponse`/`invalidResponse`),
   `generation_pipeline_test.dart` (production-граф, 401), `redaction_test.dart`.
3. **L30 остаётся в `journal/KNOWN_LIMITATIONS.md` как частично закрытое:** success-путь DeepSeek — закрыт
   (2026-11-14), остальные контракты — известное ограничение по решению владельца, отдельного шага в плане нет.
4. **Пересмотр — только новым ADR:** если появится тестовый ключ/аккаунт, требование приёмки или сообщение
   о расхождении поведения провайдера с ожидаемым.

## Последствия

- Живые негативные прогоны в план не включаются; вопрос не поднимается в следующих сессиях заново.
- Контракты 401/429/`Retry-After` на реальном API остаются неподтверждёнными. Риск снижен тем, что обработка
  кодов и ретраи — единый транспорт (`GenerationHttpClient` + `RetryPolicy`, ADR-012), покрытый тестами,
  и успешный live-вызов доказал, что общий путь запроса/ответа/валидации работает на реальном сервисе.
- Live-тест остаётся детерминированным и не флакует из-за лимитов провайдера; на CI он self-skip.
- Полное снятие L30 (все провайдеры и негативные пути) — только при новом решении владельца; L1 (ключи
  OpenAI/Gemini/Anthropic) и L32 (Ollama/LM Studio) остаются открытыми независимо.
