# ADR-055 — контекст «уже создано» в запросе v3 и правило его усечения

**Статус:** принято (2026-11-28, срез 17B генерации v3). **Контекст:** срез 17
показал, что v3 проигрывает прежнему пути по доле смысловых дублей на учебном
тексте (24,4–51,1 % против 0–3,5 %), и зафиксировал, что работа над дублями — это
промпт (S18), а не метрика. Срез 17B проверил одну гипотезу: **v3 не сообщает
модели, что уже создано в прогоне**. Запрос v3 нёс только принятое **текущего**
батча (`<already_accepted>`), тогда как прежний путь с среза 13 шлёт
`<already_created>` — дайджест лицевых сторон всех принятых карточек
(`generation_pipeline.dart:_digestOf`). Гипотеза: если v3 покажет краткие
утверждения уже принятых единиц и занятые `unit_id`, модель перестанет
повторять уже покрытые факты.

## Решение

1. **У прогона v3 появляется второй контекст — «уже создано».**
   `RunCardContext` (`lib/domain/generation/run_card_context.dart`): краткие
   утверждения единиц, по которым карточка уже **принята**, и занятые `unit_id`.
   Источники:
   - этап Generation (`CardsBatchEngine`): контекст пополняется **по завершении
     партии** — принятое текущей партии остаётся в `<already_accepted>`, чтобы не
     дублировать его в запросе;
   - этап Replenish (`ReplenishStage`): контекст пересобирается перед каждым
     запросом из накопленного принятого — добор идёт по уже покрытым единицам и
     без контекста повторял бы их «вторым углом» вслепую.
2. **В запрос уходят не полные карточки, а утверждения.** Утверждение единицы —
   одна мысль, которую модель не должна повторять; лицевая и обратная стороны
   чужих карточек не передаются (иначе модель начнёт копировать формулировки
   вопросов/ответов). Формат блока:

   ```
   <already_created>
   <taken units="ku:…#0 ku:…#1"/>
   <statement unit_id="ku:…#0">утверждение единицы</statement>
   </already_created>
   ```

3. **Формулировка `gen-cards-v3` не меняется.** TASK среза 17B запрещает править
   промпт: меняется только то, что модели показывают. Блок — данные запроса, а не
   инструкция; `docs/prompts/gen-cards-v3.txt` и его байтовая сверка не тронуты.
4. **Предел роста payload — по числу, а не по байтам.**
   `kRunContextMaxStatements = 20`, `kRunContextStatementMaxChars = 160`,
   `kRunContextMaxTakenUnits = 40`. Усечение делает сборщик сообщения
   (`buildCardsUserContent`), поэтому обойти предел нельзя, даже передав в партию
   длинный контекст. Приоритет при усечении — утверждения разделов текущей партии
   (тот же приём, что у legacy `_digestOf`), затем остальные в порядке принятия.
   Тест «200 принятых единиц дают тот же запрос, что 50» фиксирует отсутствие
   роста.
5. **Повтор утверждения по единице — один.** У единицы может быть до четырёх
   карточек (углов); в контексте она представлена одним утверждением, потому что
   повторять модели нечего — факт один.

## Замер (TASK ч. 2–4)

Одна ячейка: учебный материал, заказ 150, `deepseek/deepseek-flash`, потолок
0,30 USD. База — **оплаченная** ячейка `textbook-v3-150` среза 16 (контекста не
было). Числа — `journal/generation-v3/matrix-s17b.md`, протокол — `verify-s17b.md`.

- В живом прогоне контекст **дошёл** до платного запроса: 1 из 3 карточных
  запросов нёс `<already_created>` с 20 утверждениями и занятыми `unit_id`
  (запись — `request_shapes` в `live-s17b/run.json`).
- **Критерий «снизил dupRate» не выполнен:** `dupRate` 24,4 % → 39,1 %
  (предрегистрация — `verify-s17b.md` §0: строго ниже, `unique ≥ 0,8 × базы`,
  `cleanRate` не ниже −5 п.п.).
- Причина структурная, а не «контекст вреден»: при профиле `deepseek-flash`
  (`maxOutputTokens = 384 000`) весь заказ умещается в **один** запрос генерации —
  в нём `<already_created>` пуст по построению, а 25 дублей родились **внутри
  одного ответа**. Контекст, который сообщает о других партиях, физически не
  может повлиять на такой ответ.
- Дополнительное искажение: карта Understanding строится заново в каждом прогоне
  (33 → 41 единица, ёмкость плана 56 → 73), поэтому разница `dupRate` двух ячеек
  не атрибутируется правке (L238).

**Следствие:** TASK п. 11 — дубли уходят в промпт `gen-cards-v3` (S18). Правка
не откатывается: она делает v3 совместимым по информации с прежним путём, покрыта
тестами и не меняет план/пороги; но она **не объявлена выигрышем** и не служит
основанием включать v3 по умолчанию (`auto` = legacy, `kGenerationPathV3MinUnits
= null`).

## Следствия

- Информация о прогоне перестаёт зависеть от размера батча: у любого следующего
  запроса есть краткий срез «что уже создано», усечённый по числу.
- Формат и пределы закреплены тестами (`run_context_test` 6, `cards_prompt_test`
  дополнен, `replenish_stage_test` +1, `generation_v3_facade_flow_test` зелёный),
  поэтому смена лимитов — правка констант с тестом, а не «подкрутка промпта».
- Живой замер пишет форму запросов числами (`LivePayloadProbe`), а не текстами:
  «дошёл ли контекст» проверяется фактом, а не предположением.

## Ограничения

- L238: одна ячейка на путь и материал; карта Understanding между прогонами
  разная, поэтому сравнение не изолирует правку.
- L239: на профиле с большим `maxOutputTokens` заказ умещается в один запрос —
  контекст между партиями в такой ячейке не проверяется вовсе; для проверки нужен
  профиль с меньшим пределом вывода или материал, не влезающий в один ответ.
- L237: слепая выборка среза 17B собрана (60 карточек, 30 v3 + 30 legacy), но
  разметка владельцем — вне прогона; доля годных считается после заполнения
  (`tool/blind_score_s17b.dart`).
