# ADR-057 — Устойчивое открытие БД: бэкап — best-effort, восстановление повреждённого файла

**Дата:** 2026-11-28 · **Статус:** принято (итерация «Починка базы данных и миграции») · **Связано:** ADR-005 §5, ADR-051, SPEC A6.6/A8.6; `lib/data/db/database_opener.dart`, `lib/main.dart`, `lib/ui/app.dart`; тесты `test/unit/data/db/{schema_test,database_recovery_test}.dart`, `test/widget/app_test.dart`

## Контекст — инцидент 2026-11-28

Владелец запустил Windows-релиз `1.0.2+3` и получил экран «Не удалось открыть базу
данных. Перезапустите приложение»: приложение полностью неработоспособно, при этом
его реальная БД (14 колод, 392 карточки, 448 повторений, 163 медиа) осталась на
версии схемы 1 и не менялась по mtime.

**Диагностика (факты, не гипотезы):**

1. Файл БД владельца цел: `PRAGMA integrity_check = ok`, `foreign_key_check` пуст,
   `user_version = 1`, все таблицы v1 на месте.
2. Копия этого файла, открытая production-путём (`openAppDatabase` + миграции
   1 → 2 → 3 на `NativeDatabase.createInBackground`), успешно мигрирует до v3:
   данные сохранены, `user_version = 3`, `.bak` создаётся. То есть **миграция
   исправна**, баг не в `onUpgrade` и не в `PRAGMA foreign_keys`.
3. Реальный сбой — **копирование файла перед миграцией**: `backupBeforeMigration`
   падал с `PathAccessException: Cannot copy file ... (OS Error: Отказано в
   доступе, errno = 5)`, и это исключение выходило из `openAppDatabase`, минуя
   обработку «повреждённый файл». Экран ошибки — следствие именно этого шага.
4. Причина отказа в доступе — **внешняя среда, а не приложение**: процессы, чей
   исполняемый файл лежит в каталоге проекта, запускаются с **Low integrity**
   токеном (`S-1-16-4096`), поэтому не могут создавать/менять файлы в
   `%APPDATA%` и `%TEMP%` (mandatory integrity control). Проверено контрольно:
   - та же сборка из `C:\Temp\...` запускается с `S-1-16-8192` (Medium) и
     открывает БД, мигрирует её и показывает приложение;
   - `notepad.exe`, скопированный в каталог проекта, тоже получает Low, а он же
     в `Downloads`/`Desktop` — Medium;
   - эффект не зависит от родителя: запуск из `WmiPrvSE.exe` даёт тот же Low.
   Это ограничение среды агента (`DSH_SHELL=1`, sandbox рабочего каталога), а не
   дефект CardFlow; но именно оно вскрыло слабые места старта.

**Слабые места приложения, которые превратили внешний отказ в «кирпич»:**

- бэкап перед миграцией был **условием** открытия: любая ошибка копирования
  (права, занятый путь `.bak`, нехватка места) блокировала запуск;
- не было аварийного восстановления: нечитаемый/повреждённый файл БД означал
  вечную ошибку старта без возможности запустить приложение;
- миграции выполнялись **лениво** (первый запрос), поэтому сбой файла мог
  всплыть позже и в произвольном месте, а не как ошибка старта;
- экран ошибки не различал «нет прав» и «файл повреждён», хотя действия
  пользователя в этих случаях разные.

## Решение

1. **Бэкап — страховка, а не условие старта.** `backupBeforeMigration` ловит
   любые сбои и возвращает `false`; открытие БД продолжается. Копия `.bak`
   по-прежнему делается только при `user_version < currentSchemaVersion`.
2. **Аварийное восстановление повреждённого файла (ADR-057 §2).**
   `openAppDatabaseWithRecovery` открывает БД и **применяет миграции до возврата**
   (eager, чтобы сбой был ошибкой старта). Если открытие упало, причина
   определяется **прямой пробой файла** `sqlite3` в том же изоляте (drift в
   фоновом изоляте оборачивает ошибку SQLite в `DriftRemoteException`, поэтому
   без пробы тип причины неотличим): читается `PRAGMA user_version` и пишется
   обратно то же значение (проверка прав на запись; значение не меняется).
   Проба даёт `SQLITE_NOTADB` (26) / `SQLITE_CORRUPT` (11) → файл вместе с
   `-journal`/`-wal`/`-shm` переименовывается в
   `cardflow.sqlite.corrupted_<yyyyMMdd_HHmmss>`, и на его месте создаётся новая
   пустая БД. Старый файл **не удаляется**, поэтому данные можно достать вручную.
   Проба идёт только в пути сбоя — успешный старт её не платит.
3. **Fail-fast сохранён для остальных причин.** Понижение версии
   (`user_version` новее приложения), неизвестный шаг миграции, занятый файл,
   отсутствие прав — ошибка открытия, файл не переименовывается: молча
   пересоздавать БД, где могут быть данные, нельзя (ADR-005 §5). Восстановление
   срабатывает только на «файл не является базой данных».
4. **Пользователь узнаёт о восстановлении.** `CardFlowApp` принимает
   `recoveredDatabaseFileName` и после первого кадра показывает SnackBar
   `databaseRecoveredNotice` (ARB): «Файл базы данных был повреждён. Его копия
   сохранена в папке данных, создана новая база». Молчаливая потеря данных
   запрещена.
5. **Экран ошибки различает причины.** `StartupErrorApp(accessDenied: true)`
   добавляет подсказку `databaseOpenAccessHint` («проверьте права на папку
   данных»), когда `isDatabaseAccessFailure` распознал `SQLITE_PERM/READONLY/
   CANTOPEN/AUTH` или `FileSystemException`. Сырые исключения в UI не попадают
   (SPEC A8.6); в `debugPrint` — только тип сбоя, без путей и данных.

## Альтернативы

1. **Всегда пересоздавать БД при любой ошибке открытия** — теряются данные при
   временных сбоях (BUSY, нет прав) и при понижении версии; отклонено.
2. **Никогда не пересоздавать (текущее поведение ADR-005)** — повреждённый файл
   делает приложение неработоспособным навсегда; отклонено владельцем как
   «кирпич».
3. **Аварийный режим «только чтение»** — сложен, требует отдельного UI и портов
   репозиториев; восстановление с сохранением файла решает задачу проще.
4. **Бэкап в памяти/временном каталоге при отказе `.bak`** — путь `.bak` и так
   рядом с БД; если каталог недоступен для записи, недоступен и временный путь
   приложения. Отклонено.

## Последствия

**Плюсы:** запуск больше не зависит от успеха копирования; повреждённая БД
восстанавливается автоматически, а исходный файл сохраняется; сбой файла виден
на старте; пользователь получает понятную причину и уведомление о
восстановлении; поведение покрыто тестами на реальных файлах.

**Минусы/риски:** (а) восстановление — это потеря расписания и карточек из
активной БД (файл остаётся рядом, но приложение его не читает); (б) eager-открытие
добавляет к старту один запрос и чтение файла БД (миграции всё равно выполнялись
бы на первом запросе); (в) повреждение **страницы данных** (не заголовка), при
котором проба проходит, автоматически не восстанавливается: приложение покажет
экран ошибки, файл останется цел — сознательный выбор в пользу сохранности
данных; (г) Low-integrity окружение по-прежнему не даёт писать в
`%APPDATA%` — приложение в таком окружении обязано показывать ошибку, а не
притворяться работающим; запуск релиза из каталога проекта в песочнице агента —
известное ограничение L244.
