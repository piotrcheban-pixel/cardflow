# ADR-008 — Классическая сессия: состав очереди, персистентность каждого ответа, undo

**Дата:** 2026-11-13 · **Итерация:** 2 · **Статус:** принято
**Контекст SPEC:** A6.4 (каркас сессии), A7.1 (контракт режима), A7.2 (кнопки/прогноз/haptics), A5 (`review_logs`, правило транзакции, `fsrs_json`/`due`), A6.3 (запуск из колоды), A6.6/A6.7/A7.19–A7.20 (настройки/конструктор).

## Контекст

SPEC задаёт экран и поведение кнопок, но не фиксирует: (1) какие карточки попадают в сессию и в каком порядке; (2) что происходит с карточкой после оценки (остаётся ли она в сессии); (3) как именно работает undo; (4) какие элементы A6.4/A7.2 входят в итерацию 2. Правило A5 однозначно: `due`/`fsrs_json` обновляются в одной транзакции с `review_logs`.

## Варианты

1. **Фиксированный список, одна оценка на карточку.** Очередь строится при старте: сначала просроченные (по `due`), затем новые (по `createdAt`). Каждый ответ сразу пишется в БД (одна транзакция). Undo — компенсирующая транзакция (удалить лог + восстановить снимок карточки), стек undo в памяти сессии. Плюс: просто, детерминированно, соответствует A5. Минус: карточка, оценённая «Не знаю» (due через 1 мин), не покажется снова в этой сессии.
2. **Requeue обучаемых карточек (как в Anki).** При Again/Good карточка возвращается в конец очереди. Плюс: соответствует шагам обучения. Минус: очередь перестаёт быть линейной, прогресс-бар и undo усложняются, спецификация этого не требует; требует отдельного решения по интервалам/нагрузке — отложено.
3. **Запись только при выходе из сессии.** Плюс: undo проще. Минус: прямо нарушает A5 («обновляются в одной транзакции с записью review_logs»), риск потери прогресса; отклонено.

## Решение

Принимаем **вариант 1**:

- **Состав очереди** (`domain/review/review_queue.dart`): карточки колоды, у которых `suspended = 0` и не `buriedUntil > now`; входят `state = new` (новые) и `due <= now` (просроченные learning/review/relearning). Будущие `due` не входят. Порядок: просроченные — `due` ASC, затем новые — `createdAt` ASC, тай-брек `id` ASC (детерминизм тестов).
- **Одна оценка на карточку за сессию**, без requeue. Повторное предъявление learning-карточек — backlog итерации 6/отдельного ADR по обратной связи.
- **Персистентность:** каждая оценка сразу пишется одной транзакцией: `INSERT review_logs` + `UPDATE cards SET state, fsrs_json, due, updated_at`. Поля лога: `rating` 1–4, `reviewed_at` (UTC ms), `mode = 'classic'`, `scheduled_days` = `(after.due − reviewedAt)` в сутках (REAL, доли суток для шагов обучения), `actual_days` = `(reviewedAt − lastReview)` в сутках (`null` для первого повторения), `elapsed_ms` = время от показа карточки до оценки.
- **Undo:** откат последней оценки компенсирующей транзакцией — удалить строку `review_logs` по id и восстановить сохранённый снимок `state`/`fsrs_json`/`due`/`updated_at` карточки. Стек undo живёт только в памяти открытой сессии (между запусками приложения undo недоступен). После undo карточка снова текущая, ответ раскрыт (пользователь его уже видел).
- **Каркас A6.4 в итерации 2:** линейный прогресс, undo, выход с диалогом (прогресс уже сохранён — диалог это сообщает), «Почему?» (неактивна без `source_excerpt`, иначе bottom sheet с цитатой), карточка с 3D-flip по тапу/Space, панель 4 кнопок с прогнозом.
- **Вне итерации 2 (не отрисованы, «мёртвых кнопок» нет):** настройки сессии (лимит/перемешивание/интерливинг) и другие режимы — итерации 4/6; bottom sheet запуска содержит только «Классический»; кнопки A7.2 «Изменить»/«Отложить»/«Флаг» — backlog.

## Последствия

- Прогресс не теряется при выходе/сбое: каждая оценка уже в БД; диалог выхода не спрашивает «сохранить?», а информирует.
- Undo ограничен текущей сессией — это осознанно; глобальный undo (история) не входит в MVP.
- Один режим на итерацию: расширение до «Ленты» (итерация 4) использует тот же `ReviewSession`-движок и тот же `ReviewRepository`.
- Session-настройки и лимиты появятся вместе с конструктором (итерация 6) и будут менять только построение очереди, не формат записи.
