# ADR-004 — Конфигурация FSRS в MVP: параметры по умолчанию и детерминированный прогноз

**Дата:** 2026-11-11 · **Итерация:** 0 · **Статус:** принято
**Контекст SPEC:** A3 (кандидат `fsrs`), A5 (`fsrs_json`, `due`, `review_logs`), A6.6 (настройки retention/шагов), A7.2 (прогноз интервалов над 4 кнопками), A7.19.

## Контекст

SPEC задаёт поведение («прогноз над кнопкой вычисляет планировщик той же операцией, что и при оценке», A7.2), но не задаёт конкретные значения:
- `desiredRetention` — диапазон 0.7–0.95 (A6.6), значение по умолчанию не указано;
- шаги обучения/переобучения — список в настройках (A6.6), значения не заданы;
- fuzzing (случайное размытие интервалов) — не упомянут;
- веса FSRS — не заданы; подразумеваются эталонные веса FSRS-6.

Реализация итерации 0 (`lib/domain/scheduling/scheduler.dart`) должна зафиксировать стартовую конфигурацию, чтобы тесты интервалов были детерминированными, а MVP — предсказуемым.

## Варианты

1. **Эталонные значения FSRS по умолчанию**: `desiredRetention = 0.9`, learningSteps 1 мин / 10 мин, relearningSteps 10 мин, `enableFuzzing = true`, 21 вес `fsrs.defaultParameters`. Плюс: соответствует reference-реализации. Минус: fuzzing делает прогноз интервалов случайным при каждом вызове `reviewCard` — предпросмотр над кнопками «дрожит» и не совпадает с фактическим интервалом; тесты интервалов требуют контроля Random.
2. **Детерминированный MVP**: те же параметры, но `enableFuzzing = false`. Плюс: прогноз ровно совпадает с фактическим планированием (требование A7.2), тесты стабильны, UX честнее («показываем то, что будет»). Минус: карточки могут кучковаться на одну дату (fuzzing в FSRS существует именно для размытия); при небольших колодах это почти незаметно.
3. **Fuzzing только для фактического планирования, прогноз — детерминированный отдельным планировщиком**: плюс — оба свойства соблюдены. Минус: два планировщика в адаптере, прогноз может отличаться от фактического интервала на ±5–15% — нарушает буквальное требование A7.2 «той же операцией».

## Решение

Принимаем **вариант 2** для MVP:
- `FsrsScheduler` по умолчанию: `desiredRetention = 0.9`, `learningSteps = [1 мин, 10 мин]`, `relearningSteps = [10 мин]`, `maximumInterval = 36500` дней, `enableFuzzing = false`;
- веса — `fsrs.defaultParameters` (21 вес, FSRS-6 reference-реализация);
- все параметры — параметры конструктора, чтобы в итерации 7 экран настроек и настройки колоды могли их менять (A6.3, A6.6);
- fuzzing включается только осознанным изменением конфигурации (например, в настройках колоды post-MVP), с одновременным решением, как показывать прогноз; это потребует обновления ADR.

## Последствия

- Прогноз над кнопками «Не знаю / Сложно / Знаю / Легко» детерминирован и равен фактическому следующему `due` — буквальное выполнение A7.2; это проверено тестом (`previewIntervals` == результат `review` по `due` для тех же входов).
- Тесты интервалов стабильны, без моков Random (`fuzzing выключен по умолчанию: прогноз детерминирован`).
- Интервалы иллюстративной таблицы A7.2 (<10 мин, 3 д, 7 д, 14 д) не «зашиты»: фактические значения вычисляет планировщик для конкретной карточки, как и требует SPEC.
- Возможная кучность повторений у больших колод — известный компромисс MVP; при необходимости включается fuzzing (тогда прогноз считается отдельно, ADR обновляется).
- Значения `desiredRetention` в 0.7–0.95 и шаги обучения будут редактируемыми в настройках (итерация 7); этот ADR фиксирует только defaults.
