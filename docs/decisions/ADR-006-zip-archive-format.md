# ADR-006 — Публичный контракт `.zip`-экспорта колоды, версия 1

**Дата:** 2026-11-12 · **Статус:** принято (итерация 1) · **Связано:** SPEC 0.4 п.4 (публичный контракт), SPEC A6.9, A5, A8.5; `AGENTS.md`; `docs/archive-format.md`

## Контекст

SPEC 0.4 п.4 фиксирует: `.zip`-экспорт — **публичный контракт**: `meta.json` с `format_version`, `cards.json`, `media/`; менять только с повышением версии формата. SPEC A6.9 требует импорт с валидацией версии и дедупликацией. Точная структура JSON в SPEC не задана — её надо определить один раз и заморозить.

Требования, вытекающие из продукта и правил проекта:

- экспорт/импорт **без потерь** (MVP B3 п.5): карточки, состояния FSRS, теги, медиа, настройки колоды — сохраняются при roundtrip;
- импорт не должен быть вектором атаки: zip-slip, zip-bomb, гигантские JSON; сырые исключения пользователю не показываются (только ARB);
- импорт создаёт данные в одной транзакции (частично импортированная колода — баг);
- дедупликация по `content_hash` (SPEC A5/A8.5);
- ключи API/секреты в архив не попадают ни при каких условиях (SPEC A8.6);
- формат должен быть расширяемым: поля добавляются в следующих версиях, версия повышается при несовместимом изменении.

## Решение

Формат **версии 1** (каноническое описание — `docs/archive-format.md`):

- zip-записи: `meta.json`, `cards.json`, `media/<media_id>` (без расширения; MIME — в `cards.json`);
- `meta.json`: `format_version: 1` (int), `app: "CardFlow"`, `exported_at` (ISO-8601 UTC), `deck{id, name, settings, created_at, updated_at, archived_at}` (timestamps — epoch ms), `cards_count`, `media_count`;
- `cards.json`: массив `cards` со всеми полями таблицы `cards` (SPEC A5): `id, deck_id, front, back, hint, card_type, tags[], media[{id,card_id,path,mime_type}], latex, occlusion, source_doc_id, source_excerpt, state, fsrs, due, suspended, buried_until, flagged, sibling_id, content_hash, created_at, updated_at`; timestamps — epoch ms, nullable — JSON `null`;
- `review_logs`/`practice_logs`/`generation_jobs`/`app_settings` **не входят** в v1 (их нет в контракте SPEC 0.4 п.4); добавление — только в v2+ с повышением `format_version` и ADR.

**Правила импорта:**

1. `format_version != 1` → `ArchiveException(unsupportedVersion)`; неизвестные поля игнорируются, отсутствие обязательного — `invalidMeta`/`invalidCards`.
2. Импорт **всегда создаёт новую колоду**: id колоды и карточек генерируются заново (uuid v4), исходные id сохраняются только в `meta.json`/`cards.json` как информация; это исключает коллизии PK и перезапись существующих данных. «Без потерь» = без потери контента (все поля/медиа), не идентификаторов.
3. Дедупликация: нормализованный `content_hash` (`front + "\u0000" + back`, SPEC A5). Если `content_hash` в архиве `null` — вычисляется при импорте. Дубликаты **внутри архива** пропускаются (первая карточка выигрывает); количество показано в предпросмотре. Дубликаты между колодами допустимы (разные колоды — разные контексты).
4. Медиа: файлы из `media/<id>` записываются в медиа-хранилище приложения, строки — в таблицу `media`; id медиа и связи `card.media_ids` перегенерируются. Ссылка карточки на отсутствующую запись `media/<id>` → `mediaMissing` (не молчаливая потеря).
5. Импорт — **одна транзакция**: колода + карточки + медиа-строки; при ошибке откат, файлы медиа удаляются (best effort).
6. Предпросмотр (`previewImport`) не пишет в БД; показывает имя колоды, число карточек/медиа и число дубликатов.
7. Отмена выбора файла/сохранения — тихий no-op (не ошибка).
8. Имя файла экспорта предлагается как `<имя колоды>.zip` с заменой символов, недопустимых в ФС (`/\:*?"<>|`) на `_`; пустое имя → `cardflow.zip`.
9. **Сохранение файла на платформах:** контракт `FileGateway.saveZipFile({suggestedFileName, bytes})` объединяет выбор места и запись, потому что `file_picker 13.3.3` на мобильных платформах сам записывает байты и возвращает `content://`-URI, с которым `dart:io` не работает; на desktop плагин возвращает путь к файлу, и реализация дописывает байты через `dart:io`. `false` от шлюза = пользователь отменил (тихий no-op).
10. Пустые directory-записи вида `media/` (0 байт, имя оканчивается на `/`) допускаются и игнорируются — так могут вести себя сторонние архиваторы; любые другие неизвестные записи → `invalidEntryName`.

**Безопасность:**

- zip-slip: имена записей с `..`, абсолютные пути, обратные слэши, записи вне `{meta.json, cards.json, media/<plain-id>}` → `invalidEntryName`;
- лимиты: входной zip ≤ 100 МБ (`DeckArchiveLimits.maxImportBytes`), распакованный суммарный объём ≤ 300 МБ, `meta.json`/`cards.json` ≤ 32 МБ каждый → `tooLarge`;
- JSON парсится с проверкой типов; сырые `FormatException`/`ArchiveException` не показываются пользователю — маппинг в ARB по машинному коду;
- секреты не экспортируются (в архиве их нет по схеме); guard `no_secrets` остаётся зелёным.

**Версионирование:** любое несовместимое изменение (удаление/переименование/смена типа поля, новые обязательные поля) → `format_version + 1`, новый ADR, поддержка импорта предыдущих версий (v1) — минимум одна версия назад. Совместимые добавления необязательных полей допускаются без смены версии только если импорт игнорирует неизвестные поля.

## Последствия

**Плюсы:** формат зафиксирован документом (`docs/archive-format.md`) и тестами кодек+сервис; roundtrip без потерь проверяется автоматически; импорт безопасен и транзакционен; добавление review-логов — через v2.

**Минусы/риски:** (а) id при импорте меняются — внешние ссылки на карточки (например, в будущих шарингах) должны опираться на `content_hash`; (б) review-история не переносится в v1 — это осознанное ограничение контракта SPEC 0.4 п.4; (в) медиа-файлы без расширения — потребителю нужен MIME из `cards.json`; (г) лимиты 100/300 МБ — не проверены на реальных больших архивах (в итерации 1 медиа не создаются); запись в KNOWN_LIMITATIONS при необходимости.
