# ADR-053 — дубль не закрывает слот, ёмкость по богатству, метрика попыток

**Статус:** принято (2026-11-28, срез 16 генерации v3). **Контекст:** перемер
среза 15 показал `cleanRate(v3)` 30–47 % против 95 % порога и объяснил это
пометкой `possible_duplicate` (срез 13): дубль закрывал слот, попадал в журнал
запуска и только потом помечался. Второе слагаемое — константа «4 карточки на
единицу» (срез 14): план заказывал четыре вопроса об одном коротком
утверждении, а модель отвечала дублями.

## Решение

1. **Dedup — до принятия, а не после генерации.** Каскад `SemanticMatcher`
   (`CandidateDeduper`, `lib/domain/generation/candidate_deduper.dart`)
   спрашивается в момент приёма карточки — в первом проходе
   (`CardsBatchEngine`) и в доборе (`ReplenishStage`). Кандидат-дубль
   **откладывается**: не идёт в `CardSink`, не закрывает слот, но считается
   попыткой (`duplicates` в журнале). Новых правил дедупликации нет — тот же
   каскад ADR-050 §3.4.
2. **Один повтор на слот с другим углом.** Отложенный слот остаётся долгом;
   повтор запрашивается с первым свободным углом порядка вида
   (`angleCycleFor`), а не с тем же вопросом. `ReplenishPolicy.maxAttemptsPerSlot
   = 2` распространён на дубли: вторая смысловая коллизия по тому же слоту
   закрывает его как `ReplenishStopReason.duplicates` (класс — уже существующий
   `ShortfallKind.duplicates`), третьего запроса нет.
3. **Ёмкость единицы — функция богатства.** Вместо `kMaxCardsPerUnit` как нормы
   (4 карточки каждой единице) — `unitCapacity`: одна карточка плюс надбавки за
   значимость (`salience ≥ 0.8`), составной якорь (≥ 3 утверждений/клауз) и
   вид «формула/процедура»; потолок — прежние 4. `allocationCapacity` и
   `materialCapacity` считаются той же функцией, поэтому «материала примерно на
   N карточек» уменьшается — это ожидаемое следствие, а не регресс.
4. **Метрика — попытки, а не только принятое.** `OutcomeCounts`
   (`lib/domain/generation/outcome_counts.dart`) из одного `GenerationReport` для
   обоих путей: `attempted` = принято + отброшено + дубли, `accepted`, `unique`
   (принятые без пометки дубля), `clean` (принятые без любых пометок), доли
   `cleanRate/dupRate/blockRate` — от `attempted`. Legacy-путь дополнительно
   отдаёт в `duplicates` те дубли, которые удаляет `_acceptCard` (поведение
   приёма не меняется).
5. **Критерий флага среза 16:** `cleanRate(v3) ≥ 95 %` **и**
   `dupRate(v3) ≤ dupRate(legacy)` **и** `absoluteClean(v3) ≥ absoluteClean(legacy)`
   на всех решающих ячейках (база меньше `kMinMatchedUnits = 10` единиц —
   нерешающая). Решение — числами `journal/generation-v3/live-s16/matrix-s16.md`,
   а не намерением.

## Последствия

- Пометка `possibleDuplicate` в принятом больше не появляется на пути v3:
  дубль не принимается. Пометки этапа Dedup (`saveDedupMarks`, L219) остаются в
  хранилище для старых журналов и снимков, но новый прогон их не пишет — писать
  нечего.
- Журнал запуска (`card_drafts`) не получает отложенных дублей: импорт их не
  видит. Число, причина (две коллизии → слот закрыт дублем) и уровни каскада
  видны в отчёте (`duplicates`, `duplicatesByLevel`, `shortfallReasons`).
- Legacy не удалён и не менялся по поведению; промпты `gen-cards-v3`/`gen-map-v1`
  заморожены — сдвиг метрики объясняется аллокацией и порядком этапов.
- Знаменатель метрики — все попытки, поэтому строгий путь не выглядит чище от
  того, что отбрасывает больше.
