# ADR-040 — Whole-document-first, распределение карточек, партии и `gen-ru-v8`

**Дата:** 2026-11-20 · **Итерация:** 7.18 «Планирование генерации» ·
**Статус:** принято.
Связано: SPEC A8.1/A8.4/A8.5; ADR-015/021/024/029/031/037; аудит
`journal/iteration-7.18/audit.md` §5.3–5.7, §8; ADR-039.

## Контекст

Аудит 7.18 показал, что сейчас:

- бюджет входа зависит от заказа карточек: `_limitTarget =
  min(requested, cardsByOutputCap)` передаётся в `GenerationBudget.compute`
  (`generation_chunk_planner.dart:679–704`), поэтому **разбиение документа
  меняется от числа карточек**;
- есть продуктовая мягкая цель «6000 токенов материала на карточку»
  (`:68,713–717,732–757`) — она дробит материал задолго до исчерпания окна;
- целый документ никогда не проверяется целиком: нет шага «сначала уменьшить
  резерв вывода, потом резать вход»;
- карточки распределяются по объёму текста фрагмента (`_distributeLimits`,
  `:2092–2126`), а не по разделам и их насыщенности; разделов как единиц
  распределения нет;
- фрагмент = запрос: число партий жёстко равно числу частей, `focus` нет,
  сводки уже созданных карточек для материаловых запусков нет;
- схема ответа без `section_id`/`source_exhausted`, сообщение без `<outline>` и
  `<task>`, неизменного префикса для кэширования нет.

## Решение

### 1. Три независимых решения

| Решение | Класс | Вход | Не зависит от |
|---|---|---|---|
| Input Planner | `InputPlanner` | разделы, `ModelLimits`, бюджет входа, точность оценки | **количества карточек** |
| Card Allocator | `CardAllocator` | разделы (вес/ёмкость), заказ | числа частей и партий |
| Output Batch Planner | `OutputBatchPlanner` | `InputPlan`, `CardAllocation`, потолок карточек на ответ | числа частей (только материалов, в которых работает) |

`InputPlanner` **не принимает** `requestedCards`: единственные числа, которые он
использует, — бюджет входа и резерв вывода `R` (§3). `desiredOutputTokens`
(сколько токенов ответа хочется) вычисляется до вызова и влияет только на
«уменьшить резерв/дробить» — при этом `R` для дробления берётся от
`batchCardsCeiling`, а не от заказа, поэтому **число частей одинаково при
заказе 10, 50 и 100**.

### 2. `GenerationPlanningConfig` (домен, чистый Dart)

```
tokensPerCard          = 300     // средняя карточка; калибруется по usage
outputFill             = 0.85    // доля max_tokens под карточки
schemaOverhead         = 200     // служебные токены JSON-ответа
minBatchCards          = 5       // минимальная осмысленная партия
batchCardsCeiling      = 40      // потолок карточек в одном ответе
estimateMargin         = 0.10    // запас, если вход — оценка
exactMargin            = 0.03    // запас, если вход посчитан нативно
unknownContextMaterial = 6000    // legacy-допущение при неизвестном окне
unknownContextOutput   = 2048    // legacy-допущение вывода
defaultOutput          = 8192    // если модель не сообщает лимит

tokensFor(n)  = ceil((n × tokensPerCard + schemaOverhead) / outputFill)
cardsFor(t)   = floor((t × outputFill − schemaOverhead) / tokensPerCard)
desiredOutput = min(maxOutput, tokensFor(min(max(requested, minBatchCards), ceiling)))
```

`tokensPerCard = 300` заменяет прежние 1024 (`generation_budget.dart:23`).
Обоснование: 300 — **средняя** карточка, а не максимальная; хвост больших
карточек покрывается `outputFill = 0.85` и восстановлением `truncated`
(та же партия с половиной карточек), а фактический коэффициент калибруется по
`usage` (§7). Числа T1–T9 задания сходятся только с 300.

### 3. Бюджет одного запроса

- `P` — служебная часть: системный промпт, обёртка протокола, схема, `<wishes>`,
  `<outline>`, хвост `<task>` с фиксированным плейсхолдером `<cards>`;
  считается **тем же сборщиком сообщения**, что и production.
- `D` — материалы части: текст разделов и изображения каталога.
- `m` — 0.03 при нативном подсчёте (`exact`), иначе 0.10.

```
inputTokens = ceil((P + D) × (1 + m))
ограничения (каждое — только если значение известно):
  total:      inputTokens + maxTokens ≤ contextTokens
  maxInput:   inputTokens ≤ maxInputTokens            // без повторного вычитания
  output:     maxTokens ≤ maxOutputTokens
  байты:      requestBytes ≤ maxRequestBytes           // отдельно от токенов
```

**Уточнение 7.18.3 — состав входа не смешивается.** Бюджет собирается из трёх
явно разных величин (`RequestBudget`, `NativeInputCount`):

```
nativeInputTokens   — ровно то, что вернул count_tokens (с мультимодальными
                      частями: Anthropic image/document base64, Gemini inlineData)
estimatedExtraTokens — то, чего провайдер не посчитал (Gemini responseSchema),
                      оценка тем же оценщиком плана, помечена component'ом
marginTokens         — запас: 3 % если нативно посчитано ВСЁ, иначе 10 %
effectiveBudgetTokens = nativeInputTokens + estimatedExtraTokens + marginTokens
```

`accuracy = exact` только при `estimatedExtraTokens == 0`; «точный текст +
оценённые изображения/схема» — `estimated`. В UI «Подробнее» число провайдера,
добавка, резерв и плановый бюджет — отдельные строки; бюджет не выдаётся за
результат `count_tokens` (§3.5.1). Если нативный подсчёт недоступен/упал —
`nativeInputTokens = null`, бюджет строится оценкой `P + D` с запасом 10 %.

`room` для whole-document: при `totalInputPlusOutput` — `context − inputTokens`;
при `inputOnly` — `maxOutputTokens`; при неизвестной семантике — как у total
(консервативно). `maxTokens = min(desiredOutput, room)`. Если
`maxTokens ≥ tokensFor(minBatchCards)` — **wholeDocument**; иначе fragmented.
Неизвестное окно: `Dmax` консервативно 6000 токенов материала, предупреждение
`contextUnconfirmed`; гигантский непроверенный запрос не отправляется.

### 4. Input Planner — сначала весь документ

Стратегии: `InputStrategy { promptOnly, wholeDocument, fragmented }`.

1. Предварительная проверка всего запроса тем же сборщиком; при нативном
   подсчёте (Anthropic `count_tokens`, Gemini `countTokens`) — один вызов на
   план, кэш по хэшу содержимого (текст + дайджесты байтов частей + MIME +
   подписи каталога); состав точности (`native`/`estimated`/`reserve`) хранится
   в плане (7.18.3, §3). Мультимодальные части уходят в подсчёт в том же виде,
   что в production: Anthropic — base64 `image`/`document`-блоки, Gemini —
   `inlineData` внутри `generateContentRequest`; Gemini `responseSchema` в
   подсчёт не отправляется и оценивается отдельно (L163).
2. Сначала уменьшать резерв вывода, а не резать документ (формула выше).
3. Fragmented: `R = min(maxOutput, tokensFor(batchCardsCeiling))` **не зависит
   от заказа**; `Dmax = floor((limit − R) / (1 + m)) − P_part`, где `limit` —
   контекст (total) или `maxInputTokens` (inputOnly; тогда `R` не вычитается, а
   проверяется отдельно), `P_part` включает компактное оглавление.
   `n = ceil(D / Dmax)`, целевой размер `D / n`, сбалансированная упаковка по
   иерархии границ: документ → раздел → подраздел → абзац → предложение →
   безопасное деление по рунам (не разрывать суррогатные пары и формулы `$…$`).
   Если часть не влезла — повторить с `n + 1`. Пустых частей нет, порядок
   документа сохраняется.
4. Каждая часть получает имя документа, **компактное оглавление** (только
   заголовки, ≤ 3 % бюджета; при превышении уровни сворачиваются), отметку
   «часть k из n, разделы X–Y», короткие стабильные id разделов `sN`.
5. Перекрытие — только если раздел разрезан внутри: 1–2 последних абзаца
   предыдущей части как `<context_only>` с запретом делать по ним карточки;
   `origin unit ids` сохраняются, перекрытие не учитывается в покрытии.
6. Изображения/вложения: статусы `sentToModel`, `catalogOnly`,
   `unsupportedModel`, `omittedBudget`, `omittedPayload` (существующие, новые не
   вводятся). Изображение не удаляется молча; при нехватке байтов это
   `omittedPayload` + предупреждение плана. При делении и восстановлении
   изображения переходят вместе со своим разделом. Поддержка изображений —
   трёхзначная (7.18.3 §4): `supported`/`unsupported`/`unknown`; только
   подтверждённое `unsupported` оставляет изображения в каталоге (документные)
   или делает план невыполнимым (вложения пользователя). `unknown` отправляет
   части и добавляет предупреждение `imagesVisionUnconfirmed` — отсутствие
   подтверждённых данных не блокирует запуск.
7. Ошибки парсинга/нечитаемые PDF/пропущенные страницы попадают в inventory и в
   предупреждения плана (существующие `omitted`/`ParserErrorCode`).

### 5. Card Allocator

Единица распределения — раздел. `density ∈ [0.5, 1.5]` по локальным признакам
на 100 значимых слов: определения («— это», «называется», «понимают»,
«определяется как»), числа и даты, формулы `$…$`, пункты перечислений, строки
таблиц, латинские термины в русском тексте; служебные разделы (оглавление,
литература, колонтитулы) → `density = 0`, `capacity = 0`.

```
weight   = meaningfulTokens^0.8 × density
capacity = ceil(meaningfulWords / 40 × density)
```

Ключевые слова пожеланий, совпавшие с заголовком (основа — первые 5 букв),
умножают вес на 1.5. Распределение — метод наибольших остатков с ограничением
ёмкостью (water-filling): разделы на ёмкости фиксируются, остаток
перераспределяется по весу среди прочих, равные остатки делятся по порядку
разделов; при `requested ≥` числа значимых разделов каждому минимум 1.
`Σ = min(requested, Σcapacity)`; при `Σcapacity < requested` —
`achievable = Σcapacity` и предупреждение «запрошено N, достижимо ~M»
(существующий UI). Prompt-only разделы не распределяет: заказ делится на
партии.

### 6. Output Batch Planner

`cardsPerBatch = min(batchCardsCeiling, cardsFor(maxTokens))`.

- **wholeDocument:** все партии используют один полный материал; каждая партия
  получает `focus` — непрерывный по порядку документа набор разделов, сумма
  распределённых карточек которых ≈ размеру партии. Партии делятся
  сбалансированно: 100 карточек / 7 партий → 15, 15, 14, 14, 14, 14, 14.
- **fragmented:** партии строятся внутри каждой части по распределению её
  разделов; число партий не выводится из числа частей.
- Если заказ помещается в один ответ, запрос ровно один.
- Байты изображений передаются только с партией, в `focus` которой входит их
  раздел (в whole-режиме это не дублирует все изображения в каждой партии).

### 7. `gen-ru-v8`, сообщение и схема

**Имя.** В репозитории уже существует `gen-ru-v7` (ADR-037, L76:
`system_prompt.dart:15,328–329`, `docs/prompts/gen-ru-v7.txt`). Задание 7.18
требовало «новую версию — v7», но это имя занято. Решение: новый
планировочный промпт — **`gen-ru-v8`**; v5/v6/v7 остаются в коде и
`docs/prompts/` с прежними байт-в-байт тестами; `systemPromptVersion = 'gen-ru-v8'`,
тесты версии обновляются (это не ослабление: старые версии продолжают
защищаться своими тестами).

Порядок блоков — неизменный префикс одинаков во всех запросах запуска:

```
<materials>   разделы с короткими стабильными id: «Файл: имя», «## [s3] Заголовок» …
<images>      каталог id | файл | подпись | контекст
<outline>     только при fragmented
<wishes>
────────── изменяемый хвост ──────────
<task>
  <part>k из n</part>              (fragmented)
  <focus>s3, s4, s5</focus>         (карточки только по этим разделам)
  <cards>N</cards>
  <context_only>…</context_only>    (перекрытие, без карточек)
  <already_created>…</already_created>
</task>
```

- `<already_created>` — компактный дайджест: `front` уже принятых карточек,
  обрезанный до 80 символов, сначала из тех же и соседних разделов, бюджет
  ≤ 5 % входа. Полные карточки не передаются.
- Схема ответа: корень `{ "cards": [...], "source_exhausted": boolean }`,
  у карточки добавлено `section_id: string|null`; все поля в `required`
  (strict-совместимость). Терпимый локальный разбор принимает v5/v6/v7 без
  новых полей.
- Новые правила промпта: карточки только по `focus`; `<context_only>` — только
  контекст; не повторять темы из `<already_created>`; ровно N карточек или
  меньше, если материал исчерпан, и тогда `source_exhausted: true`; не выдумывать
  факты, которых нет в материалах (семантика prompt-only не меняется).
- Anthropic: `cache_control: ephemeral` на последнем неизменном блоке — только
  после проверки документации в фазе 4; если адаптер/протокол не подтверждает,
  остаётся без `cache_control` (фиксируется в `KNOWN_LIMITATIONS.md`).

### 8. Выполнение, покрытие, исчерпание, дедупликация, восстановление

- Запросы выполняются последовательно существующим `GenerationPipeline`, с
  прогрессом «запрос K из M», отменой и частичным успехом.
- Покрытие: у раздела `planned / generated / accepted`; принадлежность карточки
  разделу — по `source_excerpt`, найденному в тексте раздела; `section_id` от
  модели — подсказка.
- Исчерпание: `source_exhausted: true` или принято < 50 % запрошенного в партии
  → оставшиеся партии этих разделов отменяются; недостача **один раз**
  перераспределяется на разделы с оставшейся ёмкостью; повторных кругов нет.
- Дедупликация: существующий `content_hash` + почти-дубли в пределах запуска
  (символьные триграммы нормализованного `front`, сходство ≥ 0.85); сверка с
  карточками целевой колоды сохраняется.
- Восстановление (≤ 3 операций на запрос, ≤ `max(3, M/2)` на запуск):
  `truncated` → та же партия с вдвое меньшим числом карточек (вход не дробить);
  переполнение — **только** 413 или 400 с распознанным сообщением провайдера
  (паттерны по протоколам) → переплан этой части с бюджетом × 0.8 (whole →
  fragmented, часть делится), числа из сообщения идут в диагностику, сохранённые
  лимиты и настройки не меняются автоматически; прочие 400/401/403 — без
  переплана; 429/5xx/таймауты — `RetryPolicy`; `json_parse` — один повтор.
  Принятые карточки не теряются, повтор не создаёт дубликатов.
- `generation_jobs`: `chunk_count` — число частей входа, `tokens_used` —
  фактический расход; метрики плана (стратегия, части, партии, запросы, оценка
  и факт токенов, повторы, восстановления, утилизация контекста) — в debug
  `GenerationDiagnostics` без содержимого документов.

### 9. Калибровка `tokensPerCard`

`generation.calibration` v1 в `app_settings` (схема БД не меняется): по
`accountId+modelId` хранятся замеры `completion_tokens / принятые карточки`;
`tokensPerCard` = экспоненциальное среднее, применяется после ≥ 2 замеров;
у reasoning-моделей замер сам включает токены рассуждения, до замеров —
явный резерв (`assumption`).

### 10. UI

- Поле «Желаемое количество карточек» — существующее
  (`generation-cards-count`), второе поле не создаётся; значение проходит
  UI → `GenerationRunRequest` → план → распределение → партии → конвейер →
  предпросмотр и сохраняется при «Повторить неудавшиеся»; тихого обрезания нет
  (технический предел — `int.max`, не продуктовый).
- Карточка «План генерации» над «Сгенерировать» пересчитывается при изменении
  файлов, количества или модели (с задержкой): строки про весь документ,
  N смысловых частей, M последовательных запросов, неподтверждённый контекст,
  «материала хватает примерно на M карточек из N»; в «Подробнее» — модель и
  источники лимитов, контекст, точность оценки, части, партии, статусы
  изображений, верхняя граница токенов и стоимость (только при известном
  тарифе).
- Настройки модели: контекст, максимальный вход/выход, вход изображений; у
  каждого значения источник («API провайдера», «Каталог», «Ваша настройка»,
  «Предположение», «Неизвестно») и дата проверки; «Обновить характеристики»,
  ручной ввод и «Сбросить к автоматическому».
- Итог после генерации: запрошено, создано, причина недобора, разделы без
  карточек.

## Последствия

- D.1 (`generation_budget.dart`) и мягкая цель 6000 заменяются формулами §3–4;
  старые константы-допущения остаются только как legacy-значения конфигурации.
- `GenerationChunkPlanner` сохраняет публичный API (`plan(...)`), но внутри
  собирает план из трёх независимых решений; `GenerationPlan.chunks` — по
  одному на запрос (партию), плюс план получает `inputStrategy`, части,
  распределение, `focus` и покрытие.
- Число частей перестаёт зависеть от заказа (T4); перезапросы не меняют
  сохранённые лимиты модели.
- Изменение контракта требует обновления тестов бюджета/планировщика
  (новые числа — контракт T1–T9), но не ослабления assertions.

## Ограничения

- Точного токенизатора провайдера нет; нативный подсчёт — только там, где
  документирован (Anthropic/Gemini). Оценка — консервативная эвристика.
- `tokensPerCard` до калибровки — допущение; калибровка требует прогонов, живые
  запросы в этой итерации запрещены.
- Кэширование префикса и `cache_control` проверяются байтовым тестом префикса и
  unit-тестами адаптера; фактическое попадание в кэш провайдера без живого
  прогона не подтверждается.
