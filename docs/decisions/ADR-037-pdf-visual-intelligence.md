# ADR-037 — PDF Visual Intelligence: изображения из PDF и сканов

**Дата:** 2026-11-18 · **Итерация:** L76 «PDF Visual Intelligence» · **Статус:** принято

## Контекст

Ограничение **L76**: изображения внутри PDF-страниц не извлекались. DOCX/PPTX/ODT
отдавали `DocumentImage` ещё с итерации fix-gen, а PDF — только текстовый слой:
`pdfrx` (PDFium) умеет `loadText()` и рендер страниц, но не даёт доступ к объектам
страницы (Image XObject, Form XObject). Сканы отправлялись страницами PNG
(ADR-023/027), и модель видела целую страницу без привязки к `image_id`.

Следствия ограничения:

- графики, схемы, диаграммы, формулы-картинки и фотографии из PDF не попадали
  в карточки;
- в смешанном PDF (часть страниц текстовая, часть — скан) страницы скана
  обрабатывались только целиком и только как вложение;
- модель не могла вернуть `image_id` для изображения из PDF, а значит и
  привязать картинку к вопросу/ответу.

Требование итерации: извлекать, обрабатывать, сохранять и использовать
визуальное содержимое PDF при генерации карточек, поддерживая обычные PDF,
PDF со встроенными изображениями и полностью сканированные PDF; модель должна
**видеть** изображения (vision), а не только их идентификаторы.

## Решение

### 1. PDFium через `pdfium_dart` в воркер-изоляте `pdfrx`

- `pdfium_dart` 0.4.1 уже был в графе транзитивно (`pdfrx → pdfium_flutter →
  pdfium_dart`): это те же FFI-биндинги, которые использует `pdfrx`. В
  `pubspec.yaml` он объявлен прямым (`^0.4.1`) и запинен под `pdfrx 2.12.0`;
  нового нативного стека нет (один `pdfium.dll`/`libpdfium.so` из build-hook).
- Добавлен `ffi ^2.2.0` (выделение нативной памяти для `FPDF_LoadMemDocument64`
  и структур PDFium; тоже уже был в графе).
- **Критично (спайк итерации):** FFI-вызовы `pdfium_dart` из «своего» изолята
  падают, если PDFium уже инициализирован в воркер-изоляте `pdfrx`
  (`Cannot invoke native callback from a different isolate`). Поэтому
  извлечение выполняется **в воркер-изоляте `pdfrx`** через
  `PdfrxEntryFunctions.instance.compute(...)` — сериализованно с остальными
  вызовами PDFium. Это же снимает вопрос потокобезопасности PDFium.

### 2. Два независимых пути извлечения

**Обычный PDF (Image XObject).** `PdfImageExtractor`
(`lib/api/parsers/pdf_image_extractor.dart`):

- обходит объекты страницы (`FPDFPage_GetObject`), рекурсивно заходит в
  Form XObject (`FPDFFormObj_CountObjects`/`GetObject`) — изображения внутри
  форм тоже извлекаются;
- для каждого изображения берёт метаданные (`FPDFImageObj_GetImageMetadata`:
  исходные пиксели, bpp, цветовое пространство), положение
  (`FPDFPageObj_GetBounds` + матрица формы для вложенных объектов) и порядок;
- **растр в исходном разрешении:** `FPDFImageObj_GetRenderedBitmap` отдаёт
  картинку в размере на странице (скан 1224×1584 при 612×792 pt → 612×792),
  поэтому PDFium растеризует **область страницы** с масштабом
  «пиксели изображения / размер на странице» (`FPDFBitmap_Create` +
  `FPDF_RenderPageBitmap`) — качество не теряется, цвета/маски/прозрачность
  обрабатывает сам PDFium; раст в размере отображения — только резерв при сбое;
- guard-лимиты: ≥ 32 px по стороне, ≤ 16 млн пикселей, ≤ 60 изображений,
  длинная сторона PNG ≤ 2600 px.

**Скан (страницы без текста).** `PdfScanPageExtractor`
(`lib/api/parsers/pdf_scan_pages.dart`) — рендер страниц (`PdfScanRenderer`,
ADR-023/027, ≤ 3 страницы) + `PdfPageRegionDetector`
(`lib/api/parsers/pdf_page_regions.dart`):

- страница целиком сохраняется как `DocumentImage(source: renderedPage)` —
  контекст для vision-модели и повторной обработки;
- детектор ищет связные области «чернил» (сетка анализа, дилатация,
  компоненты, склейка), отбрасывает строки текста (их обрабатывает текстовый
  слой/vision) и вырезает значимые области **из полного рендера без
  масштабирования** — `DocumentImage(source: croppedRegion)` с номером
  страницы, порядком и прямоугольником в долях страницы;
- страница с одной большой схемой (≥ 55 % площади) сохраняется целиком,
  отдельные вырезки не делаются;
- «OCR» в этой архитектуре — vision-модель на полном рендере страницы
  (ADR-023/027): локального OCR-движка в проекте нет и отдельная тяжёлая
  зависимость не добавлялась (см. «Ограничения»).

### 3. Постраничная классификация

`PdfPageClassifier` (`lib/api/parsers/pdf_page_classifier.dart`): для каждой
страницы `textLayer` (≥ 50 символов текста), `scanned` (короткий текст +
изображения) или `blank` (ни текста, ни изображений). Смешанный PDF
обрабатывается постранично: текстовые страницы дают разделы и встроенные
изображения, страницы-сканы — рендер и области; области страниц без текста
привязываются к ближайшему текстовому разделу (`page` при этом сохраняется).
Полностью сканированный PDF по-прежнему отдаёт `scannedPdf` — его страницы
уходят провайдеру как image-part, но теперь дополнительно с областями.

### 4. Модель `DocumentImage` — обратно совместимое расширение

Добавлены `source` (`embedded`/`renderedPage`/`croppedRegion`), `rect`
(`DocumentImageRect`, доли 0..1) и `order`; `page` остаётся номером страницы.
Значения по умолчанию (`embedded`, без координат) сохраняют поведение
DOCX/PPTX/ODT. Схема БД и `format_version` не менялись.

### 5. Фильтрация мусора

`PdfImageFilter` (`lib/api/parsers/document_images.dart`): отбрасывает иконки,
тонкие линии/разделители и однотонные плашки, дедуплицирует повторы по
SHA-256. Размер — не единственный критерий: небольшие изображения на странице
с подписью рисунка/схемы/формулы (`pageHasFigureContext`) сохраняются.

### 6. Vision: модель видит изображения, а не только `image_id`

- `CardGenerationService` при `account.supportsVision` добавляет к запросу
  image-части документов (`selectVisionDocumentImages`: приоритет — подпись →
  значимая область/встроенное изображение → площадь; ≤ 8 изображений и ≤ 24 МБ
  на запрос, дедуп по SHA-256).
- Перед каждой частью идёт текстовая часть с той же строкой каталога
  (`img3 | файл | подпись | стр. 2`): модель однозначно сопоставляет увиденное
  с `image_id` (поле `GenerationAttachment.label`, поддержано во всех трёх
  адаптерах — OpenAI/совместимый, Gemini, Anthropic).
- Каталог `<images>` остаётся полным: не вошедшие в лимит изображения
  доступны по `image_id`, байты разрешаются при импорте.
- Модель без Vision получает прежний текстовый каталог (поведение DOCX).

### 7. Промпт `gen-ru-v7`

`gen-ru-v6` сохранён дословно; v7 = v6 + блок «ИЗОБРАЖЕНИЯ ИЗ PDF И СКАНОВ»
(текст задания + правила чтения каталога: страница, подпись перед частью,
приоритет полной страницы/области, поведение при усечении). Копия —
`docs/prompts/gen-ru-v7.txt`, тест сверяет байты.

### 8. MediaStore

Парсер изображения в `MediaStore` не пишет (как и DOCX): байты живут в памяти
до импорта, файл и строка `media` появляются только у импортированной карточки
(`DriftGenerationCardStore` + `MediaStore`), поэтому GC медиа не удаляет
извлечённое и нет параллельного хранилища. Сквозной путь «PDF → изображение →
модель → `image_id` → `MediaStore`» покрыт интеграционным тестом
`test/integration/pdf_image_flow_test.dart`.

## Лицензии

| Пакет | Версия | Лицензия | Роль |
|---|---|---|---|
| `pdfium_dart` | 0.4.1 (прямая, та же, что в `pdfrx`) | BSD-3-Clause | FFI-биндинги PDFium |
| `ffi` | 2.2.0 | BSD-3-Clause | нативная память для вызовов |
| PDFium (библиотека) | `chromium/8125` (build-hook, CI пин) | BSD-3-Clause | извлечение объектов/растр |
| `image` | 4.12.0 | MIT | декод PNG, крой областей, кладка альфы |

`syncfusion_flutter_pdf` не добавлялся: коммерческая лицензия (community-лицензия
требует условий Syncfusion, pub.dev license-tag `unknown`) — см. `docs/dependencies.md`.
`pdfx`/`flutter_pdfview` не нужны: рендер уже даёт `pdfrx`.

## Последствия

- Встроенные изображения PDF (включая Form XObject) привязаны к странице,
  порядку и координатам; сканы дают страницу + области.
- Модель с Vision действительно видит изображения; без Vision — прежний
  каталог (обратная совместимость).
- FFI-вызовы PDFium только из воркер-изолята `pdfrx` — правило для всех
  будущих PDF-расширений.
- Рост размера запроса на изображения ограничен лимитами (8 частей / 24 МБ).
- Схема БД не менялась; `format_version` экспорта не менялся.

## Ограничения

- Локального OCR-движка нет: текст скана распознаёт vision-модель; текстовый
  слой скана (если он есть) читается как обычно. Распознанный «текст» не
  сохраняется в `ParsedDocument` отдельным полем.
- Детектор областей — геометрический: таблицы/сложные многоколоночные сканы
  могут дать лишние или слитые области; лимит 3 области на страницу.
- Векторные схемы на страницах с длинным текстом не вырезаются (детектор
  работает только для страниц без текста и для полностраничных изображений).
- Координаты вложенных в форму изображений — в системе формы, умноженной на
  матрицу формы (композиция только по одной оси вложенности).
- Пределы: ≤ 60 изображений из PDF, ≤ 24 изображения в документе-парсере,
  ≤ 3 рендерируемые страницы (ADR-027), длинная сторона PNG ≤ 2600 px,
  ≤ 8 image-частей и ≤ 24 МБ на запрос к модели.
- Извлечение идёт в памяти: очень большие PDF (десятки страниц с huge-сканами)
  ограничены размером файла 25 МБ и guard-лимитами пикселей.
- Отмена парсинга не поддерживается (парсинг в `Isolate.run` не отменяем;
  отмена генерации — на уровне пайплайна).
