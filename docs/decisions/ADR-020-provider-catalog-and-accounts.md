# ADR-020 — Каталог провайдеров и аккаунты генерации (итерация 7.5)

**Дата:** 2026-11-14 · **Статус:** принято · **SPEC:** A6.6, A6.8, A8.2, A8.5, A8.6, 3.4
**Контекст.** Владелец проверил экран настроек API и нашёл его неработающим и неудобным:
ввёл ключ DeepSeek, нажал «Сохранить» — ключ не сохранился, генерация не заработала. Нужен
экран «как в DSH»: один список провайдеров, кнопка «+ Добавить провайдера» с двумя путями
(каталог / пользовательская модель API), надёжное сохранение ключей в `flutter_secure_storage`
и немедленное использование в генерации. Итерация 7 (ADR-019 §2) знала только четыре
провайдера-энума и одну пару «адрес + модель»; DeepSeek как провайдер в UI отсутствовал.

## 1. Диагностика (факты, не предположения)

| # | Находка | Доказательство |
|---|---|---|
| D1 | Ключ не сохранялся: `GenerationSettingsScreen._save()` валидировал **адрес и модель** и делал ранний `return` до записи ключа. Экран не имел каталога, поэтому DeepSeek вводился как «OpenAI-совместимый сервер», где ключ неотделим от адреса/модели | тест `test/widget/settings/generation_settings_key_bug_test.dart` (до переписывания): `ожидалось: ключ записан (writeCalls=1), получено: writeCalls=0`; текст — `journal/iteration-7.5/red.md` |
| D2 | Генерация по умолчанию уходила в OpenAI: `GenerationScreen._defaultProvider` выбирал облачного провайдера с ключом, а `openaiCompatible` — только при заданных **и** адресе, **и** модели; статус ключа совместимого провайдера был жёстко `true` | чтение кода (`lib/ui/generation/generation_screen.dart`, итерация 3c) |
| D3 | Экран показывал «Сохранено» независимо от read-back: молчаливая потеря значения платформой выглядела как успех | `_save()` читал `storedKey`, но `settingsSaved` показывался безусловно |
| D3′ | Платформенное хранилище **исправно** (Windows): реальный плагин пишет и читает значение | `fvm flutter test integration_test/secure_api_key_store_windows_test.dart -d windows` → `All tests passed!` (DPAPI, L28 частично закрыт) |

## 2. Протоколы, каталог, аккаунты

- `ProviderProtocol` — `openai-completions`, `openai`, `anthropic-messages`,
  `gemini-generate-content`; каждый отображается в существующий адаптер `GenerationProvider`
  (переименования адаптеров нет: `lib/api/providers/` остаётся слоем протоколов).
- `ProviderPreset` + `kProviderPresets`: DeepSeek, OpenAI, Anthropic, Gemini, OpenRouter,
  Moonshot (Kimi), MiniMax, Groq, Ollama (Local) — адрес, протокол, популярные модели с окном
  контекста, обязательность ключа. Названия брендов живут в каталоге (не в ARB): это не
  переводимый интерфейсный текст (SPEC 3.1 разрешает латиницу в брендах).
- `ProviderAccount` — `id`, `label`, `presetId?`, `protocol`, `baseUrl`, `modelId`,
  `contextTokens`, `requiresApiKey`; `ProviderAccounts` — список + `activeAccountId`;
  JSON `{"version":1,...}` в одной строке `app_settings` с ключом `generation.providers`.
  **Схема БД и `schemaVersion` не меняются.**
- `id` аккаунта — стабильный slug (`deepseek`, `deepseek-2`, `provider`), потому что он же имя
  ключа в secure storage (`cardflow.api_key.<id>`). Id никогда не меняется при редактировании.

## 3. Ключи API (SPEC 3.4)

- Контракт `ApiKeyStore` стал **строковым** (id аккаунта) вместо enum-провайдера: у пользователя
  может быть два аккаунта одного протокола (два ключа DeepSeek). Legacy-имена
  (`openai`, `gemini`, `anthropic`, `openai_compatible`) совпадают с id мигрируемых аккаунтов,
  поэтому старые ключи читаются без копирования.
- Запись ключа отделена от записи аккаунта: ключ пишется **первым**, сразу после read-back
  проверяется, и только затем сохраняется аккаунт. Несовпадение read-back → сообщение
  `providersKeyStoreError`, аккаунт не сохраняется (D3).
- Значение ключа не подставляется в поле, не рендерится в текстовые виджеты и не логируется;
  редактор ключа — `obscureText`, «оставьте пустым, чтобы не менять».

## 4. Миграция наследия 3b–7

При первом чтении пустого `generation.providers`:

1. `generation.openai_compatible` (адрес + модель) → аккаунт `openai_compatible`; если адрес
   совпал с каталогом — `presetId`/бренд из каталога, иначе пользовательский аккаунт с тем же
   адресом (лейбл пустой → UI показывает «Пользовательская модель API»).
2. Legacy-ключ есть, а адреса/модели нет (симптом владельца) → неполный аккаунт
   `openai_compatible`: ключ сохраняется, адрес и модель пользователь дополняет в диалоге.
3. Legacy-ключи `openai`/`gemini`/`anthropic` → аккаунты каталога с моделью по умолчанию.
4. Результат сразу записывается; пустое наследие ничего не создаёт.

Ключи **не** копируются: id аккаунтов совпадают с legacy-именами хранилища.

## 5. UI

- `/settings/generation` — единый список карточек: бренд, протокол/модель, адрес, статус ключа,
  отметка «Основной»; действия: «Проверить подключение», «Сделать основным», «Изменить»,
  «Удалить». Внизу (в `bottomNavigationBar`, ретро 3c) — «+ Добавить провайдера».
- Диалог добавления: «Сторонний поставщик» (каталог → адрес и модели заполняются автоматически,
  вводятся только модель и ключ) и «Пользовательская модель API» (название, протокол, адрес,
  модель, ключ).
- «Проверить подключение» — `ApiKeyVerifier` минимальным запросом существующими адаптерами;
  наружу только статус: «Подключение работает» / «Ошибка ключа» / «Нет подключения» / лимит / не настроен.
- Блок «API» на экране настроек — сводка аккаунтов и переход к экрану провайдеров; отдельные
  строки OpenAI/Gemini/Anthropic и селектор «модель по умолчанию» удалены. **Следствие:**
  `AppSettings.defaultProvider/defaultModelId` больше не существуют (провайдер по умолчанию —
  `activeAccountId` аккаунтов); старый JSON `app.settings` читается (неизвестные ключи
  игнорируются), схема строки не менялась.
- Экран генерации: чипы — аккаунты, модель — из моделей пресета выбранного аккаунта; выбор по
  умолчанию — основной аккаунт; баннеры «Провайдеры не настроены» / «Ключ доступа не задан».

## 6. Генерация (A8.2, A8.5)

- `GenerationRequest`/`GenerationRunRequest` несут `ProviderAccount` вместо пары
  `provider + modelId`; `CardGenerationService` выбирает адаптер по протоколу, ключ — по
  `account.id`, адрес и модель — из аккаунта; спец-ветка «OpenAI-совместимый» из сервиса ушла
  (правило: `openai-completions` → один fallback без strict-схемы, остальные протоколы — без fallback).
- Все адаптеры уважают `baseUrl` аккаунта (`ProviderEndpoint`): официальные адреса — значения
  по умолчанию протокола, пользовательские (прокси, шлюз) задаются аккаунтом.
- `generation_jobs.provider` = **id аккаунта** (диагностика «куда ушёл запрос»), `model` = модель;
  схема таблицы не менялась.

## 7. Последствия и отклонения

- `ApiKeyStore`, `GenerationRequest`, `GenerationRunRequest`, `ApiKeyVerifier.check` — breaking
  изменения внутри проекта; все вызывающие обновлены, тесты переписаны под аккаунты.
- Удалены `GenerationModel`/`kGenerationModels` (каталог моделей переехал в пресеты) и настройка
  «модель по умолчанию» (её роль играет основной аккаунт). Тесты, описывавшие удалённое
  поведение, переписаны/удалены осознанно — см. `journal/iteration-7.5/`. SPEC и критерии
  остановки MVP не правились.
- `integration_test` (Flutter SDK) добавлен в dev-зависимости только для проверки реального
  secure storage на Windows (L28); в CI-матрицу не входит.
- Открытые вопросы владельцу: нет (все развилки решены простейшим совместимым вариантом).
