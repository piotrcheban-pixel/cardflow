# OpenAI-совместимый провайдер: DeepSeek, Ollama, LM Studio

**Дата:** 2026-11-13 · **Статус:** решение — ADR-013; живая проверка ожидает ключ
(`journal/KNOWN_LIMITATIONS.md` L30) · **Связано:** SPEC A8.2, A8.4, A8.6; ADR-011; ADR-012;
ADR-013; `docs/api-schema.md` §2, §5, §7

## 1. Что это

CardFlow умеет вызывать не только OpenAI, Gemini и Anthropic, но и любой сервер с Chat Completions API:
пользователь сам задаёт адрес сервера, модель и (необязательно) ключ. Один и тот же провайдер покрывает:

- **DeepSeek** — облачный сервис, https, ключ обязателен;
- **Ollama** — локальный сервер, http, ключ не нужен;
- **LM Studio** — локальный сервер, http, ключ не нужен;
- любой другой совместимый сервер (vLLM, llama.cpp-серверы, корпоративные шлюзы) — по тем же правилам.

Ответ сервера проверяется той же канонической схемой A8.4 и тем же локальным валидатором, что и у
остальных провайдеров: качество карточек не зависит от того, какой сервер выбран.

## 2. Настройка

Настройки задаются на экране **«Настройки генерации»** (блок провайдера — «OpenAI-совместимый сервер»):

| Поле | Что вводить |
|---|---|
| «Адрес сервера» | Корень API с протоколом: `https://…` или `http://…`. Путь `/v1` (если он есть у сервера) сохраняется |
| «Модель» | Имя модели на сервере (вручную: списка моделей у произвольного сервера нет) |
| «Ключ доступа (необязательно)» | Ключ облачного сервиса. Сохранённый ключ не показывается: чтобы заменить — введите новый, чтобы удалить — оставьте поле пустым и сохраните. Для локальных серверов ключ не нужен |

Что происходит при сохранении:

- адрес и модель сохраняются в `app_settings` (ключ `generation.openai_compatible`);
- ключ (если введён) — только в защищённом хранилище (`flutter_secure_storage`);
- в БД, экспорт и логи ключ не попадает (правило 3.4, ADR-012 §4).

Правила адреса:

- только `http`/`https`; `https` рекомендован для облачных серверов, `http` — для локальных и доверенных
  (локальная сеть, самодельный сервер). `http` не запрещён, но передача ключа по нему — ваш риск: ключ и
  материалы идут по сети открытым текстом;
- логин/пароль в адресе (`user:password@…`), query и fragment запрещены — ключ передаётся только
  заголовком `Authorization`;
- адрес — корень API, путь `/chat/completions` приложение дописывает само. Полный адрес эндпоинта
  вставлять не нужно; повторно путь не добавится.

Один активный совместимый сервер: чтобы сменить сервер, отредактируйте адрес и модель. Профили нескольких
серверов в MVP не поддерживаются.

## 3. Примеры

| Сервис | Адрес сервера | Модель (пример) | Ключ |
|---|---|---|---|
| DeepSeek | `https://api.deepseek.com` (допустим и `https://api.deepseek.com/v1`) | `deepseek-chat` | обязателен |
| Ollama | `http://localhost:11434/v1` | имя из `ollama list`, например `llama3.2` | не нужен |
| LM Studio | `http://localhost:1234/v1` | идентификатор загруженной модели | не нужен |

Итоговый запрос: `<адрес сервера>/chat/completions` — например,
`https://api.deepseek.com/chat/completions` или `http://localhost:11434/v1/chat/completions`.

## 4. Порядок запроса и fallback

1. **Строгий запрос** — как у OpenAI: `response_format: {type: "json_schema", json_schema: {strict: true,
   schema: <канон A8.4>}}`.
2. **Если сервер не поддерживает strict** и отвечает ошибкой `badRequest` (любой 4xx: 400, 404, 422 и
   т.п.; 401/403/429 сюда не входят) — **один** повтор того же запроса без `response_format`. Это не
   ретрай: 4xx транспортом не повторяются (ADR-012), повтор выполняется осознанно и только один раз.
3. **Локальная проверка** — ответ в обоих случаях декодируется и проверяется канонической схемой A8.4 и
   контентными правилами. Послаблений из-за fallback нет: невалидная схема — `invalidResponse`, карточки
   фрагмента не импортируются.
4. **JSON в markdown-ограждении или в пояснительном тексте** извлекается до декодирования — локальные
   модели иногда отвечают «текстом», даже когда их просят только о JSON. Это не отменяет проверку схемы;
   остальные провайдеры по-прежнему обязаны вернуть чистый JSON.
5. При 401/403, 429, 5xx, таймауте и сетевой ошибке fallback не выполняется — работают обычные коды ошибок
   и ретраи ADR-012.

Лимит токенов ответа не передаётся (как у OpenAI, ADR-011 §3): число карточек ограничивает `<limit>`, а
обрезание распознаётся по `finish_reason`. Причина остановки проверяется по колонке OpenAI
(`docs/api-schema.md` §3).

## 5. Ошибки и что делать

| Симптом | Код | Что сделать |
|---|---|---|
| «Сервер не настроен. Укажите адрес и модель в настройках» | `providerNotConfigured` | Заполнить адрес и модель (или исправить адрес, отклонённый валидацией) — запроса в сеть не было |
| «Ключ доступа недействителен…» | `invalidApiKey` | Проверить ключ в настройках (401/403) |
| «Запрос отклонён. Проверьте выбранную модель и ключ в настройках» | `badRequest` | Проверить имя модели и адрес: сервер отверг запрос (после fallback — значит, и без `response_format` тоже) |
| «Нейросеть вернула неожиданный ответ…» | `invalidResponse`/`truncated`/`refused`/`emptyResponse` | Повторить; при повторе — сменить модель/сервер (схема не соблюдена, ответ пуст, отказ или обрезка) |
| «Нет подключения к интернету» | `timeout`/`network` | Проверить адрес и доступность сервера |
| «Превышен лимит запросов…» | `rateLimited` | Подождать N секунд (облачные сервисы) |

Сырые ответы сервера, исключения и `details` пользователю не показываются — только строки интерфейса (ARB).

## 6. Live-проверка

Живые вызовы **ещё не выполнялись**: ключа DeepSeek в окружении нет, локальные Ollama и LM Studio не
подняты. Статус зафиксирован в `journal/KNOWN_LIMITATIONS.md` (L30); «проверено» не заявляется, пока
live-прогон не подтверждён.

Параметры live-тестов (тег `live`; без ключа — skip, в обычный прогон не входят):

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `DEEPSEEK_API_KEY` | — (без ключа live-тест пропускается) | ключ DeepSeek |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com` | адрес совместимого сервера |
| `DEEPSEEK_MODEL` | `deepseek-chat` | модель |

Что проверяет live-прогон:

- сборка URL без двойного `/chat/completions`;
- отсутствие заголовка `Authorization`, когда ключ не задан (локальный сервер);
- fallback: при `badRequest` (любой 4xx, кроме 401/403/429) на strict-запрос выполняется ровно один повтор
  без `response_format`;
- извлечение JSON из markdown-ограждения и текста вокруг него;
- маппинг причин остановки (`length`, отказ, пустой ответ) и кодов ошибок;
- редактирование `Authorization` в логах: значение ключа в выводе не встречается.

## 7. Ограничения

- Один активный совместимый сервер; профили нескольких серверов — post-MVP.
- Списка моделей нет: имя модели вводится вручную (ошибка в имени — `badRequest`).
- Строгий режим `response_format` поддерживают не все серверы; выручает один fallback без
  `response_format` с локальной валидацией схемы (см. §4).
- `http` не запрещён (нужен для локальных и доверенных серверов), но `https` рекомендован для облачных;
  передача ключа по `http` — риск на стороне пользователя, жёсткой проверки localhost нет.
- Доступность и качество сервера — ответственность пользователя: CardFlow не проверяет сервер заранее,
  первый запрос — генерация.
- Ключ необязателен: локальные серверы обычно работают без аутентификации.
- Отдельной кнопки проверки ключа нет; проверка ключа A6.6 — отдельная задача.
- Живые контракты DeepSeek/Ollama/LM Studio не проверены (L30).

## 8. Безопасность

- Ключ — только `flutter_secure_storage` (`ApiKeyStore`, ключ `cardflow.api_key.openai_compatible`);
  в `app_settings`, БД, экспорте и `generation_jobs` его нет.
- `Authorization` редактируется перехватчиком логов (`***`); тела запросов и ответов не логируются —
  материалы и ответ модели в логи не попадают (ADR-012 §3).
- Ключ не передаётся в URL: адрес с логином/паролем, query или fragment отклоняется.
- Материалы уходят только на адрес, указанный в настройках. Для локального сервера это ваша машина или
  локальная сеть; для облачного — выбранный сервис.
