<mission>
Сейчас CardFlow дробит материал по внутренним искусственным правилам и иногда использует
выдуманные значения контекстного окна. После итерации генерация должна планироваться на основе:
(1) реальных характеристик выбранной модели с указанием происхождения каждого числа;
(2) фактического размера полного запроса;
(3) количества карточек, которое запросил пользователь.

Три решения принимаются независимо и не подменяют друг друга:
- **Input Planner** решает, отправлять материал целиком или частями (только по бюджету входа);
- **Card Allocator** решает, сколько карточек дать каждому разделу (по смысловой насыщенности);
- **Output Batch Planner** решает, сколько карточек просить в одном ответе (только по бюджету выхода).
</mission>

## 3. Целевая архитектура

### 3.1. Характеристики модели и их происхождение (domain, чистый Dart)
```dart
enum CapabilitySource { userConfigured, providerApi, officialCatalog, assumption, unknown }

/// Значение конкретного параметра + откуда оно взялось.
final class Sourced&lt;T&gt; {
  final T? value;
  final CapabilitySource source;
  final DateTime? observedAt;   // когда получено (для providerApi/userConfigured)
  final String? sourceRef;      // URL документации/эндпоинта БЕЗ query-параметров
}

enum ContextSemantics { totalInputPlusOutput, inputOnly, unknown }

final class ModelLimits {
  final Sourced&lt;int&gt; contextTokens;
  final ContextSemantics contextSemantics;
  final Sourced&lt;int&gt; maxInputTokens;     // отдельный лимит входа, если документирован
  final Sourced&lt;int&gt; maxOutputTokens;
  final Sourced&lt;int&gt; maxRequestBytes;    // технический предел payload протокола
  final Sourced&lt;bool&gt; supportsImageInput;
  final Sourced&lt;bool&gt; supportsPdfInput;
  final Sourced&lt;bool&gt; isReasoningModel;  // max_tokens включает рассуждения
  final Sourced&lt;ModelPricing&gt; pricing;   // USD за 1M input/output, если известно
}
```

**Слияние по каждому полю отдельно**, от высшего приоритета к низшему: `userConfigured` → `providerApi` (в том числе устаревшее, но последнее успешное) → `officialCatalog` → `assumption` → `unknown`. Если значение пользователя расходится со значением API, в UI видны оба, а в план идёт значение пользователя. Рядом кнопка «Сбросить к автоматическому».

**Миграция legacy-данных.** Контекст из `ProviderAccount`, введённый пользователем, получает источник `userConfigured`. Значение, пришедшее из пресета, становится `officialCatalog` только если у пресета есть `sourceRef` и дата проверки; иначе это `assumption`. Инференс `supportsVision` по имени (ADR-022) больше не считается подтверждением: значение остаётся рабочим, но с источником `assumption` и меткой в UI. Discovery его перезаписывает.

### 3.2. Discovery (api) и кэш (data)

- Порт в domain: `ModelCapabilityDiscovery { Future<DiscoveryResult> discover(ProviderAccount, {CancelToken?}) }`. Реализации — отдельный resolver на каждый протокол или провайдера в `lib/api/models/` со своим парсером. **Универсальный JSON-парсер для всех провайдеров запрещён.**
- HTTP идёт только через существующий `GenerationTransport` и `provider_endpoint.dart`, с таймаутом (подключение ~10 с, ответ ~20 с), отменой, `RedactingLogInterceptor` и `redactSecretsInText` в диагностике. Discovery никогда не вызывает генерацию и платные эндпоинты.
- Кэш хранится в `app_settings`, ключ `generation.model_capabilities`, JSON `version: 1`. Ключ записи — `accountId + protocol + нормализованный baseUrl + modelId`. TTL — 7 дней. Устаревшая запись используется до успешного обновления. Ошибка обновления не стирает последнее удачное значение, а пишет `lastErrorCode` и `lastAttemptAt`. Смена `baseUrl` или `modelId` даёт новую запись. **Смена ключа API** инвалидирует записи аккаунта по событию сохранения ключа; ключ и его хэш в кэш не попадают.
- Когда обновляется кэш: при сохранении аккаунта или модели; в фоне при открытии экрана генерации или настроек модели, если запись устарела (это не блокирует экран); по кнопке «Обновить характеристики». **Построение плана никогда не обращается к сети за метаданными** — только к кэшу.
- Произвольный `baseUrl`: те же правила схемы и хоста, что у генерации; http разрешён только для localhost/Ollama, если так уже принято в `provider_endpoint.dart`. Редиректы на другой хост не выполняются.

### 3.4. Бюджет одного запроса (domain)

Обозначения:
- `P` — служебная часть: системный промпт, обёртка протокола, схема в запросе, `<wishes>`, оглавление, хвост `<task>`. Считается **тем же сборщиком сообщений, что и в production**.
- `D` — материалы части: текст, каталог изображений и токены вложений.
- `m` — запас: 0.03, если подсчёт точный (нативный count_tokens), и 0.10, если это оценка.
```
inputTokens = ceil((P + D) × (1 + m))
Ограничения (каждое — только если значение известно):
  total-семантика:  inputTokens + maxTokens ≤ contextTokens
  maxInputTokens:   inputTokens ≤ maxInputTokens        // без повторного вычитания выхода
  выход:            maxTokens ≤ maxOutputTokens
  байты:            requestBytes ≤ maxRequestBytes       // считается отдельно от токенов
```

Параметры вывода собраны в `GenerationPlanningConfig`; значения по умолчанию обоснуй в ADR:
- `tokensPerCard` (tpc): начальное значение 300, затем калибровка — экспоненциальное среднее фактических `completion_tokens / принятые карточки` по `accountId+modelId` в `app_settings` (`generation.calibration` v1, применяется после ≥ 2 замеров). У reasoning-моделей калибровка сама учитывает токены рассуждения; до замеров добавляется явный резерв на рассуждение (`assumption`);
- `outputFill = 0.85` — какую долю `max_tokens` можно занять карточками;
- `schemaOverhead = 200` — служебные токены JSON-ответа;
- `minBatchCards = 5` — минимальная осмысленная партия;
- `batchCardsCeiling = 40` — потолок карточек в одном ответе ради качества и таймаутов. Это ограничение **на один запрос, а не на весь заказ**; оно видно в деталях плана.
```
tokensFor(n)   = ceil((n × tpc + schemaOverhead) / outputFill)
cardsFor(t)    = floor((t × outputFill − schemaOverhead) / tpc)
desiredOutput  = min(maxOutputTokens, tokensFor(min(requested, batchCardsCeiling)))
```

Если `maxOutputTokens` неизвестен, используй существующее в проекте консервативное значение с источником `assumption` и предупреждением.
Если неизвестен контекст и его не задал пользователь, используй существующую консервативную константу проекта, но с источником `assumption`. План получает предупреждение `contextUnconfirmed`, а UI предлагает указать контекст вручную. **Гигантский непроверенный запрос на основе предположения не отправляется.**

### 3.5. Input Planner — сначала весь документ целиком

Стратегии: `InputStrategy { promptOnly, wholeDocument, fragmented }`.

1. **Предварительная проверка всего запроса**: собрать запрос для всего материала тем же сборщиком и посчитать `inputTokens` и `requestBytes`. Если протокол поддерживает нативный подсчёт (Anthropic, Gemini), вызвать его **один раз на план**. Результат кэшируется по хэшу содержимого запроса; при ошибке используется оценка. Признак `exact/estimated` хранится в плане.
2. **Сначала уменьшать резерв выхода, а не резать документ.** `room` = место, оставшееся под ответ: при total-семантике `contextTokens − inputTokens`, иначе `maxOutputTokens`. Тогда `maxTokens = min(desiredOutput, room)`. Если `maxTokens ≥ tokensFor(minBatchCards)`, выбирается `wholeDocument` (меньшие партии лучше дробления). Иначе выбирается `fragmented`.
3. **Fragmented: минимальное число крупных частей.**
   - резерв выхода для части `R = min(maxOutputTokens, tokensFor(batchCardsCeiling))` **не зависит от числа запрошенных карточек**, поэтому разбиение входа не меняется при изменении заказа;
   - максимальный объём материалов части `Dmax = floor((limit − R) / (1 + m)) − P_part`, где `P_part` включает компактное оглавление;
   - `n = ceil(D / Dmax)`, целевой размер части `D / n`; сбалансированная упаковка по иерархии границ: документ → раздел → подраздел → абзац → предложение → безопасное деление по рунам (не разрывать суррогатные пары и формулы `$…$`). Если хоть одна часть не влезла, повторить с `n + 1`. Пустых частей не бывает; порядок документа сохраняется;
   - каждая часть получает: имя документа, **компактное оглавление** (только заголовки, не больше 3 % бюджета; если превышает — уровни сворачиваются), отметку «часть k из n, разделы X–Y»;
   - перекрытие добавляется **только** если раздел разрезан внутри: 1–2 последних абзаца предыдущей части как `<context_only>` с запретом делать по ним карточки. `origin unit ids` сохраняются, и перекрытие не учитывается в покрытии.
4. **Изображения и вложения.** Используются существующие статусы, новые вводятся только если подходящих нет: `sentToModel`, `catalogOnly`, `unsupportedModel`, `omittedBudget`, `omittedPayload`. Изображение не удаляется молча. Если по токенам всё помещается, а по байтам нет, это ограничение `requestBytes`, а не «мало контекста»: вложения распределяются по запросам по принадлежности к разделам, остаток получает `omittedPayload`, в плане появляется предупреждение. При делении и восстановлении изображения переходят вместе со своим разделом.
5. Если что-то не извлеклось из файла (ошибка парсера, нечитаемый PDF, пропущенная страница), это попадает в inventory и в предупреждения плана.

### 3.6. Card Allocator (domain, детерминированный)

Единица распределения — раздел (группа `ContentUnit` по заголовку, слайду, листу или странице). Маленькие соседние разделы допустимо склеивать до минимального размера.

- **Насыщенность раздела** `density ∈ [0.5, 1.5]` рассчитывается локальными признаками на 100 значимых слов: определения («— это», «называется», «понимают», «определяется как»), числа и даты, формулы `$…$`, пункты перечислений, строки таблиц, латинские термины в русском тексте. Оглавление, список литературы, колонтитулы и служебные разделы получают `density = 0`, `capacity = 0`.
- **Вес:** `weight = meaningfulTokens^0.8 × density`. Если в пожеланиях есть ключевые слова, совпавшие с заголовком раздела (по основе слова из первых 5 букв), вес умножается на 1.5.
- **Мягкая ёмкость:** `capacity = ceil(meaningfulWords / 40 × density)` — оценка, сколько разных фактов можно извлечь. Коэффициенты откалибруй на программных фикстурах и запиши в ADR.
- **Алгоритм:** метод наибольших остатков с ограничением ёмкостью (water-filling). Разделы, достигшие ёмкости, фиксируются, остаток перераспределяется между прочими по весу; равные остатки делятся по порядку разделов. Если заказ ≥ числа значимых разделов, каждому достаётся минимум 1. Если `Σcapacity < requested`, то `achievable = Σcapacity`, и в плане появляется предупреждение «запрошено N, достижимо ~M» (существующий UI «запрошено/достижимо» переиспользуется).
- Prompt-only режим распределения по разделам не использует: заказ делится только на партии.

### 3.7. Output Batch Planner

- `cardsPerBatch = min(batchCardsCeiling, cardsFor(maxTokens))`, где `maxTokens` — значение для конкретного запроса.
- **wholeDocument:** все партии используют один полный материал. Каждая партия получает **`focus`** — непрерывный по порядку документа набор разделов, сумма распределённых карточек которых ≈ размеру партии. Партии делятся сбалансированно (100 карточек / 7 партий → 15, 15, 14, 14, 14, 14, 14).
- **fragmented:** партии строятся внутри каждой части по распределению её разделов. Число партий не выводится из числа частей.
- Если заказ помещается в один ответ, запрос **ровно один**.

### 3.8. Сообщение пользователя `gen-ru-v7` и ответ

Новая версия системного промпта — `gen-ru-v7`. Файлы v5 и v6 сохраняются. Добавь `docs/prompts/gen-ru-v7.txt` и тест побайтовой сверки. Обнови `docs/system-prompt.md` и `docs/api-schema.md`.

Порядок блоков такой, чтобы **неизменный префикс был одинаковым во всех запросах запуска** (кэширование префикса у DeepSeek, OpenAI и Gemini; для Anthropic поставь `cache_control: ephemeral` на последний неизменный блок, если адаптер это поддерживает, после проверки документации):
```
&lt;materials&gt;  — разделы с короткими стабильными ID: «Файл: имя», затем «## [s3] Заголовок» …
&lt;images&gt;     — каталог id | файл | подпись | контекст
&lt;outline&gt;    — только при fragmented
&lt;wishes&gt;
────────── изменяемый хвост ──────────
&lt;task&gt;
  &lt;part&gt;k из n&lt;/part&gt;               (fragmented)
  &lt;focus&gt;s3, s4, s5&lt;/focus&gt;          (карточки только по этим разделам; остальное — контекст)
  &lt;cards&gt;N&lt;/cards&gt;

&lt;/task&gt;
```

- `<already_created>` — компактный дайджест: `front` уже принятых карточек, обрезанный до 80 символов, сначала из тех же и соседних разделов, общий бюджет ≤ 5 % входа. Полные карточки не передаются.

### 3.9. Выполнение, покрытие, дедупликация, восстановление

- Запросы выполняются последовательно в существующем `GenerationPipeline`, с прогрессом «запрос K из M», отменой и частичным успехом.
- **Покрытие:** у каждого раздела есть `planned / generated / accepted`. Принадлежность карточки разделу проверяется по `source_excerpt`, найденному в тексте раздела; `section_id` от модели — только подсказка.
- **Исчерпание:** если пришёл `source_exhausted: true` или принято < 50 % запрошенного в партии, оставшиеся партии этих разделов отменяются. Недостача **один раз** перераспределяется на разделы с оставшейся ёмкостью. Повторных кругов нет.
- **Дедупликация:** существующий `content_hash` плюс поиск почти-дубликатов в пределах запуска (сходство по символьным триграммам нормализованного `front` ≥ 0.85, порог в ADR); сверка с карточками целевой колоды сохраняется.
- **Восстановление** (ограничение: не больше 3 операций на запрос и не больше `max(3, M/2)` на запуск):
  - `truncated` (`finish_reason=length`/`MAX_TOKENS`/`max_tokens`): повторить **ту же партию** с вдвое меньшим числом карточек. Вход не дробить;
  - переполнение контекста — **только** 413 или 400 с распознанным сообщением провайдера (паттерны для каждого протокола, покрыть тестами). Тогда этот запрос перепланируется с бюджетом × 0.8: wholeDocument переходит во fragmented, часть делится. Числа из сообщения провайдера идут в диагностику, но **сохранённые лимиты модели и настройки пользователя автоматически не меняются**;
  - прочие 400, 401, 403 — без переплана, существующая обработка; 429, 5xx, таймауты — существующая `RetryPolicy`; `json_parse` — один повтор той же партии;
  - принятые карточки не теряются, повтор не создаёт дубликатов.
- `generation_jobs`: `chunk_count` = число частей входа, `tokens_used` = фактический расход. Метрики плана (`inputStrategy`, части, партии, запросы, оценка и факт токенов, повторы, восстановления, утилизация контекста) пишутся в debug-`GenerationDiagnostics` без содержимого документов.

## 12. Если что-то пошло не так

- **Не хватает контекста или сессия прервалась.** Действуй по протоколу возобновления из §1. Ничего не переделывай заново, пока не сверишься с `git log` и `plan.md`.
- **Тест падает после 3 попыток.** Остановись. Запиши в `journal/iteration-7.18/plan.md` гипотезы, что уже проверено и чем это кончилось, затем смени подход: сузь тест, проверь исходные данные фикстуры, перечитай реальный API класса. Ослаблять тест запрещено.
- **Формула из промпта противоречит существующему поведению или другому правилу.** Не выбирай молча. Зафиксируй противоречие в ADR, выбери вариант, который лучше соответствует миссии (честность лимитов, приоритет целого документа, независимость трёх решений), и продолжай.
- **Внешний блокер** (нет `gh`, нет Windows-раннера, нет веб-доступа). Запиши его в `KNOWN_LIMITATIONS.md` и в отчёт, выполни всё остальное.
- **Полный прогон зависает.** Проверь, что стоит `--no-pub`. Затем выполняй прогон по каталогам, чтобы найти зависающий файл, и запиши его в журнал.

1. Процесс задают `AGENTS.md` и `docs/agent-prompt.md`. `SPEC.md` не редактируется; расхождения оформляются через ADR.
