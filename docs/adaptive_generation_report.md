# CardFlow — адаптивная генерация карточек: аудит и реализация

Дата: 2026-11-22. Основание: TASK.txt (626 строк). Работа велась по схеме
«аудит → дизайн → патчи → проверка»: проектирование и логика — Claude Fable 5.2
(Chat.co API), применение патчей, анализ и тесты — локально.

## 1. Что было в архитектуре

- `lib/domain/generation/generation_chunk_planner.dart` — план строится до запросов:
  `CardAllocator` распределяет `requestedCards` по секциям, `InputPlanner` режет
  вход по бюджету, `OutputBatchPlanner` делает партии с учётом
  `maxCardsPerRequest`; `GenerationPlan.requestedCards/achievableCards`.
- `lib/api/generation/generation_pipeline.dart` (~2100 строк) — выполнение очереди
  партий, восстановление (дробление проблемной партии), дедупликация, сохранение
  прогресса, статусы.
- UI `lib/ui/generation/*` — предупреждения плана, частичный успех, предпросмотр.

## 2. Найденные проблемы

1. Добор недостачи был **однократным** (`redistributed`): цель N не добиралась
   раундами.
2. `shortfall` рос только при `sourceExhausted`/`accepted*2<limit`; обычный
   недобор (8 из 10) и отказавшие партии не учитывались — добор не запускался.
3. `_topUpChunk` получал исходный `plan`, а не `activePlan` после перепланирования.
4. `activePlan` и диагностика восстановления применялись **до** проверки бюджета:
   при исчерпанном бюджете план всё равно менялся.
5. Ожидающим партиям увеличивался `attempts`, хотя они не отправлялись.
6. Блок `on Object` не проверял отмену.
7. Статус `done` ставился даже когда `cards.length < requestedCards` — ложный успех.
8. При недоборе одной партии раздел сразу объявлялся исчерпанным — добор был
   невозможен.
9. Не было общего бюджета операции (раунды/запросы/токены/время).

## 3. Что реализовано

- **Глобальная цель**: `remaining = requestedCards − accepted`; добор ограничен
  остатком и не превышает N.
- **Многораундовый добор** (`maxTopUpRounds`, по умолчанию 4) с остановкой, если
  раунд не дал ни одной новой карточки.
- **Страйки секций** вместо мгновенного исчерпания: явный `sourceExhausted` даёт
  два страйка, слабая отдача — один; раздел исчерпан после двух.
- **Учёт недобора и отказов**: любой дефицит партии и отказавшая партия попадают
  в `shortfall`; отмена проверяется в `on Object`.
- **Честные статусы**: `done` только при достижении цели (или в авто-режиме без
  отказов); иначе `partial`; всё-дубли без новых карточек — `partial`.
- **Порядок восстановления**: перепланирование и диагностика — только после
  принятия бюджета; `attempts` не растут у неотправленных партий.
- **Бюджет операции**: `maxOperationRequests`, `maxOperationTokens`,
  `maxOperationSeconds` (0 = без лимита), точный счётчик отправленных запросов.
- **UI**: сообщение о недоборе больше не выдаёт его за исчерпание материала;
  добавлено отдельное честное сообщение «X из N, материал не исчерпан»;
  material-сообщение показывается только при реальном исчерпании секций.
- **Continuity prompt-only**: карточки попадают в продолжение после догрузки
  изображений.

Коммиты: `fcf07b2`, `47f7dfc`, `23a031f`, `fe32b98`, `76f4e13`.

## 4. Проверки

- Новые тесты: добор до цели, лимит запросов, partial без добора, матрица целей
  10/20/32/40/80/150, честный partial после недостижения цели.
- Существующие интеграционные тесты адаптированы к новой семантике (число
  запросов, статусы).
- `flutter analyze` — без замечаний (32.5 c).
- Полный `flutter test`: **2543 теста пройдено, 16 пропущено, 0 падений**.
- `flutter build windows --debug`: **успешно** (`build\windows\x64\runner\Debug\cardflow.exe`).

## 5. Оставшиеся ограничения

- Проверки качества карточек (структурная/содержательная/дубликаты/покрытие) в
  проекте уже есть; отдельный аудит их не завершён.
- Реальный прогон с платной моделью не выполнялся: тесты на фейковом клиенте.
- Android-сборка локально недоступна: в Android SDK отсутствуют cmdline-tools и
  лицензии; Windows-сборка проверяется отдельно.
- Счётчики прогресса в UI (сколько сгенерировано/осталось) отображаются частично:
  итоговые числа и причина есть, промежуточный live-прогресс требует отдельной
  доработки.
